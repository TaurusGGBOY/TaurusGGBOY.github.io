如果一个 coding agent 在执行完任务后告诉你“已经完成”，你会拿什么确认？

你可以看它的回答，也可以看仓库里的文件、测试结果和执行日志。两种方式的差别在于，前者相信模型的描述，后者检查外部环境已经发生的事实。

这正是 Sanderson Oliveira de Macedo 在论文《What makes a harness a harness》中试图回答的问题。`agent harness` 这个词已经被广泛使用，但指向并不稳定。有时它指 Claude Code、Codex CLI 这样的完整产品，有时指 SWE-bench 这样的评测脚手架，也经常和 agent framework、SDK、IDE 插件混在一起。

论文给出的判断方法很直接。一个 Agent Harness 必须同时具备四项运行时能力，也就是 Agent Loop、Tool Interface、Context Management 和 Control Mechanisms。少一项，系统就落到另一个类别里。

## 先建立一个最小模型

论文把模型、Harness 和外部环境的关系写成下面这个表达式。

```text
A = H(M, E)
```

其中 `M` 是语言模型，`E` 是文件系统、终端、浏览器或其他外部环境，`H` 是包裹模型的运行时工程层，`A` 才是能够持续完成任务的 Agent。

这个表达式的重点不在数学形式，而在职责边界。模型负责生成和判断，Harness 负责把模型接到环境上，保存上下文，推进多步执行，并在必要时限制和检查动作。

论文还追溯了 `harness` 的词义变化。这个词在英语中先后指战争装备和马具，后来进入软件工程，形成了 `test harness`。机器学习里的 `evaluation harness` 负责把模型接到标准任务上并给出分数。Agent 场景继续沿用了“连接并控制力量”的含义，但控制发生在任务执行过程中。

时间位置是这里最容易被忽略的区别。评测 Harness 在任务结束后观察结果，Agent Harness 在任务进行时影响下一步动作。

## 四个条件缺一不可

### T1 运行时循环

系统需要持续交替进行推理、行动和观察。模型决定读取文件，工具返回内容，系统把观察结果送回模型，模型再决定修改文件还是继续检查。

```text
reason → act → observe → reason → act → observe
```

如果系统只接收一次输入并返回一次输出，它是生成器或固定流水线。即使它能够调用工具，只要下一步不依赖上一步的观察结果，也没有形成论文定义里的 Agent Loop。

这里有一个很实用的区分。评测系统也可能循环运行一百个任务，但那是任务列表的外层循环。T1 关心的是单个任务内部有没有推理、行动和观察组成的自适应循环。

### T2 能改变外部环境的工具接口

工具接口需要让模型感知环境，也需要让模型改变环境。读取仓库、执行命令、写入文件、提交代码都属于这个范围。

只返回建议文本的接口不满足 T2。只能查看文件、不能修改文件的系统也不满足 T2。论文把“改变环境”作为可验证的门槛，用来排除仍停留在文本生成阶段、只挂着工具接口的包装器。

### T3 主动管理上下文

多步任务会不断产生工具输出、测试结果、错误信息和中间计划。系统必须决定哪些内容继续留在模型的上下文里，哪些内容应该被压缩、检索或移出。

机械地按长度截断历史，不足以满足 T3。论文给出的判断标准是，信息选择要依赖任务内容或当前观察，不能只看缓冲区大小。

这项条件解释了为什么上下文管理属于 Harness 的核心。Agent 如果把所有历史原样塞回模型，短任务可能还能运行，任务变长后，关键的信息会被大量中间内容稀释。上下文筛选、仓库地图、记忆和检索都在解决同一个运行时问题。

### T4 不依赖模型自觉的控制机制

系统需要至少有一种控制机制，它的效果不依赖模型“愿意遵守”。确定性验证、工具调用上限、权限模式、人工审批和沙箱都可以承担这个角色。

单独写一条提示词，要求模型不要执行危险命令，不能构成强控制。模型可以生成一段“已经完成”的说明，测试程序仍然可以检查文件和测试结果；模型可以提出转账动作，权限系统仍然可以在执行前拦截。

论文把 Guardrail 放在 Harness 内部。Guardrail 负责限制和阻断，Harness 还要负责循环、上下文、工具、重试、验证和结果回写。两者的关系是组成部分和整体。

四项条件同时满足后，系统才进入 Agent Harness 这个概念。归属是二元的，质量却可以逐步提高。一个最小系统只要能循环执行任务，并用确定性测试确认结果，也可以算作早期 Harness；它和 Claude Code、OpenHands 的差别在于控制机制的成熟度。

## 用四个问题区分相邻概念

论文把边界整理成了一组排除测试。

| 系统 | 主要职责 | 缺少的关键条件 |
| --- | --- | --- |
| Agent Framework | 组合角色、Agent 和协作协议 | 自身通常不承担完整运行时循环 |
| Agent SDK | 提供工具调用、函数定义和循环原语 | 还没有组装出正在运行的 Agent |
| IDE 插件 | 根据光标或编辑器状态生成建议 | 没有仓库级循环和独立控制 |
| Eval Harness | 运行标准任务并收集分数 | 观察任务结果，不负责任务内部的自适应循环 |
| Orchestrator | 按固定图连接预定义步骤 | 下一步由流程图决定，不由观察结果决定 |

其中最容易混淆的是 Agent Framework 和 Eval Harness。

一个 Framework 可以在每个 Agent 下面调用 Harness，负责角色分工和 Agent 协作。它解决的是“多个 Agent 怎样组合”。Harness 解决的是“一个 Agent 怎样在环境里可靠地执行”。单个 Agent 不需要 Framework，也可以拥有完整 Harness。

Eval Harness 则有另一种循环。它可以依次运行多个任务，但每个任务里的推理、工具调用和错误恢复由被测系统负责。SWE-bench 是评测体系，SWE-agent 是运行任务的 Agent 系统。两者都可能操作代码仓库，处在执行链上的位置却不同。

## 六个系统怎样通过测试

作者把 Claude Code、Codex CLI、Aider、Cline、OpenHands 和 SWE-agent 放进四项测试。六个系统都通过 T1 到 T4，所以这部分的作用主要是展示定义可以覆盖不同形态的 Coding Agent。

T4 的实现方式拉开了这些系统的差异。

- Claude Code 通过运行时防护和危险操作确认来控制动作。
- Codex CLI 通过权限模式调整 Agent 可以自动执行的范围。
- Aider 借助版本控制保留操作的可审计性和可逆性。
- Cline 在敏感操作前请求人工批准。
- OpenHands 通过沙箱隔离执行环境。
- SWE-agent 用结构化的 Agent-Computer Interface 和限制机制组织动作。

这些系统都可以被称为 Harness，但它们的控制面并不相同。论文因此把“是否属于 Harness”和“控制做得多强”拆成了两个问题。

作为边界案例，传统的代码行内补全没有通过测试。它可以根据光标生成代码，却没有围绕仓库任务形成多步循环，也没有独立验证结果。固定的“检索、生成、格式化”流水线同样没有通过，因为它的执行路径不会根据中间观察改变。

## 这篇论文解决了什么

论文没有提出新的 Agent 架构，也没有报告一个 benchmark 上的性能提升。它做的是概念整理，把工程实践里已经反复出现的机制收拢成一个可以使用的判定标准。

这个标准至少有三个用途。

第一，讨论产品时可以先问它有没有 T1 到 T4。看到“支持工具调用”或“支持多 Agent”还不够直接贴上 Harness 标签。

第二，比较两个 Agent 系统时，可以把模型能力和运行时工程分开。模型相同，循环、上下文筛选、权限和验证机制不同，最终行为也可能不同。

第三，评估 Harness 本身有了一个更清楚的起点。当前很多 benchmark 测量的是模型和 Harness 的整体结果。若要知道 Harness 的贡献，需要固定模型，再比较循环、上下文和控制机制的差异。

论文也留下了明确边界。它是一篇概念分析预印本，六个真实系统本来就被作者选作 Harness，六者通过测试并不能单独证明定义的区分力。论文的价值主要在于边界案例的排除，以及对 T1 到 T4 的可操作化。至于哪种控制机制在什么任务上最合适，还需要独立实验。

## 小结

判断一个系统是不是 Agent Harness，可以先问四个问题。

1. 它有没有根据观察结果继续决定下一步的运行时循环。
2. 它能不能通过工具改变外部环境。
3. 它有没有按任务内容主动管理上下文。
4. 它有没有不依赖模型自觉的验证、限制或隔离机制。

四个答案都为“有”，系统才跨过 Harness 的概念门槛。接下来再讨论它的速度、成本、稳定性和安全性，才有比较对象。

如果把你正在使用的 Agent 固定在同一个模型上，只替换它的上下文管理和控制机制，你能否用一组可重复的任务测出 Harness 本身带来的差异？
