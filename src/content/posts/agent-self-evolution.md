一个代码 Agent 昨天修过构建失败，今天遇到相似问题，又从头翻文件、猜原因、试命令。你提醒它“这件事之前处理过”，它才去查记录。

我们期待的进步很具体：经历一次问题之后，它能更早找到关键证据，更少重复无效尝试，并在新的任务里保持这种改善。

**本文把 Agent 自进化理解为：系统利用任务反馈，持续修改可复用的知识、技能或执行方式，并用后续表现检验修改是否有用。** 这个工作定义关注工程上的能力积累；每次修改仍然只是候选改进，可能被保留，也可能被撤回。

## 先看清：究竟是什么在变化

可以把一个 Agent 想成“模型 + 工作资料 + 工具 + 执行流程”。观察它变强时，先确定被修改的是哪一部分。

| 变化的位置 | 留下来的东西 | 下一次任务可能怎样受益 |
| --- | --- | --- |
| 记忆与上下文 | 项目事实、失败条件、解题策略 | 少查一次资料，避开已知错误 |
| 技能与执行流程 | 可复用脚本、工具封装、规划与检查步骤 | 直接复用可靠操作，调整处理顺序 |
| 模型参数 | 训练后保存的新权重 | 通过更新后的模型执行任务 |

这三层可以组合，工程成本和验证方式却不同。调用一个固定版本的模型，也能通过改进外部记忆和技能，让整个系统表现更好。Reflexion 与 Voyager 都展示了不依赖模型参数微调的改进路径。[Reflexion 论文](https://arxiv.org/abs/2303.11366)、[Voyager 论文](https://arxiv.org/abs/2305.16291)

另外要分清时间跨度。一次任务中，Agent 根据报错重试，属于当前任务的适应；把有效策略保存下来，并在后续任务中使用，才开始形成跨任务积累。给同一个问题增加尝试次数，也需要计入成本，不能直接当作持久能力的提升。

## 四条研究路线，分别留下什么

### Reflexion：把反馈变成下一轮能用的经验

Reflexion 的核心做法是：Agent 接收任务反馈，生成语言形式的反思，再把反思保留在情节记忆中，影响后续尝试。它支持不同形式和来源的反馈，模型权重不因此更新。[原论文](https://arxiv.org/abs/2303.11366)

可以用一个假设例子理解差别：“以后仔细一点”几乎没有操作信息；“修改构建配置后，要运行生产构建，因为开发服务器没有覆盖这条路径”，则给出了触发条件、动作和原因。

反思文本仍然可能判断错原因。Huang 等人在特定推理实验中发现，缺少外部反馈的内在自纠错可能无效，甚至让结果变差。这项研究针对当时的模型与实验设置，不能外推为所有模型都无法自纠错；它提示我们检查反思依据来自哪里。[研究论文](https://arxiv.org/abs/2310.01798)

### Voyager：把成功动作变成可执行技能

Voyager 在 Minecraft 中组合了自动课程、可执行代码技能库和迭代反馈。系统选择下一项任务，生成并执行程序，再利用环境反馈、执行错误与自验证改进程序；成功的技能可以保存、检索和组合。[原论文](https://arxiv.org/abs/2305.16291)

它留下的是能够再次参与行动的程序。后续任务可以借用已有技能，减少从头组织全部动作的需要。论文还检验了技能库在新 Minecraft 世界中的使用，这比只展示一次成功更接近“积累是否有用”的问题。

这里的证据范围是论文中的游戏环境。迁移到代码仓库或业务系统时，工具接口、依赖版本和成功标准都要重新处理。

### ACE：让经验手册逐步长好

ACE（Agentic Context Engineering）把上下文组织成不断演进的策略手册，通过生成、反思和整理来积累与调整内容。论文特别关注反复重写或压缩时丢失细节的问题，采用结构化、增量更新来保留有用知识。[原论文](https://arxiv.org/abs/2510.04618)

这对应一个容易理解的工程问题：总结越来越短，原先重要的条件也被总结掉了。例如，“这个旧服务在某种连接失败后需要重建客户端”，最后变成“连接失败就重启”。文本更简洁，适用范围却被错误扩大。

借鉴这条路线，可以让经验条目保留适用条件、证据出处和失效条件。这里的字段设计是工程建议，不是对 ACE 实现字段的逐项复述。

### Darwin Gödel Machine：让执行系统本身成为改进对象

Darwin Gödel Machine（DGM）进一步修改自身代码，用编码基准检验变化，并保留生成的 Agent 档案，从不同版本继续探索。它把改进对象扩展到了 Agent 的实现方式。[原论文](https://arxiv.org/abs/2505.22954)

论文报告的改变包括代码编辑工具、长上下文管理和同行检查机制。这里采用的是实验检验，不是对每次修改给出数学上的有益证明。研究也在沙箱与人工监督等条件下进行。

从工程角度看，修改范围扩大了，验证责任也随之扩大：一个工具封装的改动，可能同时影响许多原本正常的任务。

## 用一个代码修复任务，把循环串起来

下面是一个设计示例，没有对应的实测提升数字。

假设 Agent 处理一个静态网站的图片问题：本地开发时图片正常，部署后却出现空白。它先调整样式，后来通过生产构建发现，问题出在资源路径。

### 第一步：保留能还原问题的证据

记录应包括用户要达到的结果、代码版本、实际执行的命令、关键报错和修复后的页面状态。这样才能区分“构建通过”“图片请求成功”和“页面显示正确”。

Hamel Husain 与 Shreya Shankar 在 Agent 评估建议中，也把工具名称、参数、返回结果和执行后的状态分开检查。终点是用户目标是否达成，再往前定位哪一步出了问题。[评估方法](https://hamel.dev/blog/posts/evals-faq/how-do-i-evaluate-agentic-workflows.html)

### 第二步：提出一个范围明确的改进

从这次失败中，可以提出一条候选策略：

> 修改静态资源引用时，先确认项目的资源目录与生产路径规则，再执行现有生产构建；检查生成页面中的资源引用，并打开页面确认显示结果。

这条经验只覆盖相关任务。它没有要求每次改标点都重新部署，也没有把一次资源路径错误推断成所有页面故障的共同原因。

如果同类操作反复发生，还可以把“检查生成页面里的资源是否存在”封装成技能。但先看现有构建检查是否已经覆盖：如果已经覆盖，只需让 Agent 正确调用它；只有缺少这项检查、且确实发生过对应问题时，新增检查才有明确价值。

### 第三步：比较旧版本与候选版本

固定模型、工具权限与任务预算，把旧策略和新策略放到可比较的任务上运行。任务应同时包含相关图片问题，以及无需这条策略的正常修改。

我们关心的不只是哪版更容易完成图片修复，还包括它是否给简单任务增加了大量无效步骤，是否误改其他资源，以及是否需要更多人工纠正。

验证需要容纳模型输出的波动。对于受随机性影响明显的任务，要进行多次运行，并保留逐任务结果；一次碰巧成功不足以支持稳定改善。

### 第四步：保留有效变化，允许撤回

当候选策略在目标任务中表现更好，且没有造成不可接受的退步，再把它纳入常用技能或经验库。保留旧版本以及这次修改的证据，后续环境变化时可以定位和撤回。

这就形成了完整链条：**任务经验 → 候选修改 → 对比检验 → 后续使用 → 新反馈。**

## 最容易误判的三种“进步”

### 记忆增加了，但行动没有改善

存下经验之后，仍要检查检索是否命中、条件是否适用、Agent 是否实际采用，以及采用后结果怎样。如果一条记忆从未被使用，或者反复把任务带偏，它的存在本身没有证明价值。

可以做一个直接的对照：在相同任务集上分别启用和停用这条记忆，比较结果与成本。对其他因素保持控制，才更容易判断改善来自哪里。

### 分数提高了，但测量对象变了

如果 Agent 通过删除失败断言来让测试变绿，或者通过少做任务来降低耗时，指标会改善，用户目标却没有完成。这个设计中的评测程序应由独立流程维护，候选修改不能顺带改掉自己的验收标准。

数据也要分工：开发样本用于定位问题，验证样本用于选择候选方案，最终测试样本用于报告表现。反复根据同一批测试结果挑版本，这批数据就参与了选择，不能继续称为完全未参与优化的最终测试集。Eugene Yan 对评估流程的讨论同样强调基线、明确的实验预期和持续观察结果。[评估流程](https://eugeneyan.com/writing/eval-process/)

### 平均更好了，但重要任务退步了

一个候选版本可能更擅长常见问题，却更容易在少见但重要的条件下失败。除了总体完成率，还应按任务类型检查变化，并记录耗时、调用费用和人工修正量。

新增评估项应对应具体故障。比如已经观察到资源路径错误，就补足这类覆盖；无需为了显得完整，提前堆出一套与实际问题无关的评分系统。Hamel 的实践文章也建议从具体功能、场景和观察到的失败入手，并优先利用已有工具。[实践文章](https://hamel.dev/blog/posts/evals/index.html)

## 从一个值得反复解决的问题开始

如果准备给自己的 Agent 加入自进化能力，我会先选一种重复出现、结果可核验的任务，例如处理一类构建错误。先积累任务记录，找到一个稳定失败模式，再让 Agent 提出一项范围小、可撤回的修改。

这时最有用的进度记录很朴素：以前在哪些条件下会错，这次改了什么，新任务有没有改善，又付出了多少额外成本。

随着经验积累，系统可以逐渐学会更好的检索方式、工具使用顺序和技能组合；是否值得继续扩大修改范围，由这些结果决定。

**Agent 自进化最值得期待的，是一次解决问题的过程，能为下一次留下经过检验的帮助。** 当经验真正改变后续行动，并持续接受结果检验，能力才有机会积累起来。
