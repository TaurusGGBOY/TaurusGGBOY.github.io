417 小时，166 篇论文稿件，约 18.6 万美元。

这是 Analemma AI 的自动科研系统 FARS 在一次公开连续运行中留下的记录，成本包括模型调用与 GPU 使用。研究方向、实验和成稿之间的流程由 Agent 持续推进。[FARS 技术报告](https://arxiv.org/html/2606.31651v1)

看到这样的数字，很容易想到：AI 已经开始自己做研究，那么它是不是也在自己变聪明？

这里至少藏着三个问题：**研究成果有没有变好？做研究的系统有没有变好？系统调用的模型有没有学到新能力？** 三件事可以同时发生，也可以只发生其中一件。把它们分开，才能看清 Agent 自进化到底发展到了哪里。

## 一张地图：Model、Harness、Artifact

Shilong Liu 在 [A Taxonomy of Self-evolving Agents](https://lsl.zone/blog/2026/a-taxonomy-of-self-evolving-agents/) 中，用三个要素组织这个领域：模型、围绕模型的运行系统，以及系统产生的产物。模型与 Harness 组成 Agent；Agent 在环境中行动，产生 Artifact。沿着这个关系，可以分别研究产物优化、Harness 改进，以及模型学习。

| 要素 | 它具体是什么 | 一次改进可能留下什么 |
| --- | --- | --- |
| **Artifact：产物** | 程序、算法、实验方案、论文、策略 | 更快的 GPU kernel、更有解释力的实验、更好的候选解 |
| **Harness：运行系统** | Prompt、记忆、工具、技能、执行循环、协作流程 | 新规则、新工具、更合适的检索与重试方式、改过的框架代码 |
| **Model：模型** | 决定生成与行动倾向的可学习参数 | 从经验中训练得到的新权重或适配器；某些方法更新测试时的快速状态 |

![Model、Harness、Artifact 三类改进对象：模型学习，运行系统改造，产物搜索；环境反馈可以回到不同层](/images/posts/agent-self-evolution/three-targets.svg)

*同一条执行轨迹可以流向不同的改进过程。图中的回路表示可能的设计，不代表每个 Agent 都同时拥有三个回路。*

举一个贯穿全文的假设：让 Agent 优化一段数据库查询。

它把 SQL 改得更快，留下的是更好的产物；它总结出“先查看执行计划”的规则，或者写了自动比较执行计划的工具，改变的是 Harness；它把一批经过验证的优化轨迹用于训练，改变的才是模型参数。

因此，讨论自进化时，最有用的第一个问题是：**这次运行结束后，究竟哪个对象变了？**

## 第一条路线：产物自进化，把搜索交给 Agent

### AlphaEvolve：让程序进入“生成—运行—选择”的循环

程序优化天然适合反复试验：输入输出是否正确、延迟有没有下降、资源消耗是否减少，都可以通过运行来检查。AlphaEvolve 将模型生成的代码改动放进进化式搜索，借助评估反馈继续优化算法。它的应用包括数据中心调度、硬件电路简化和数学算法发现。[AlphaEvolve 论文](https://arxiv.org/abs/2506.13131)

这条路线的关键，是把模型的创造能力与执行环境接起来。模型可以提出人没有枚举过的候选，环境则提供筛选依据。一个 GPU kernel 看起来再聪明，也要经过正确性检查和实际计时。

把这个过程想成一个程序育种场会更直观：保留有潜力的版本，在它们的基础上尝试变化，再把运行结果反馈给下一轮。候选可以沿不同方向改进，例如一个更快，一个占用更少内存；搜索也就有了不同的后续起点。

**产物优化可以在模型权重固定的情况下进行。** 即使产物用于加速模型训练，也还需要分清两个环节：先发现了更好的计算方法，再由后续训练获得新的模型。两者之间有联系，但不是同一次参数更新。

### FARS：当产物从一段程序变成一项研究

FARS 把工作拆成选题、规划、实验、写作四个阶段，通过共享工作区传递假设、计划、代码、日志与结果；多个项目能够独立推进。规划阶段把研究拆成可执行步骤，实验留下可检查的记录，写作再把证据组织成稿件。持续运行依赖这些阶段之间的交接与恢复能力。[FARS 系统设计](https://arxiv.org/html/2606.31651v1#S3)

这使“产物”变得比最终 PDF 更丰富。对于自动科研，一个失败实验也可能有价值：它排除了一条思路，或者让下一轮选题避开已经走过的路。积累这些结果，才可能让计算预算不断转化成可复用的研究信息。

报告里的 166 篇是完成的稿件，不能换算成 166 篇被学术会议接受的成果。作者组织的志愿者评审覆盖其中 140 篇，发现质量差异，以及实验范围、方法和研究诚信方面的问题。[FARS 人工评审](https://arxiv.org/html/2606.31651v1#S5)

FARS 与 AlphaEvolve 也因此形成一个有意思的对照：优化 kernel，反馈可以相当直接；优化科研成果，实验是否可信、问题是否有价值、结论有没有超出证据，会同时进入判断。**产物越开放，反馈越难压缩成一个分数。**

这条路线已经很有分量。它把反复试错从人的工作时间，部分转移到了机器可以持续投入的计算过程。接下来的问题是：Agent 能否连“怎样做这些实验”也一起改进？

## 第二条路线：Harness 自进化，从经验到可执行的能力

Harness 决定模型看见什么、能做什么、怎样继续做下去。它的可修改范围很大：一句指令、一条记忆、一个工具、一套协作流程，乃至执行这些流程的源代码，都可以成为优化对象。

### Prompt：从执行轨迹里修改行为规则

手工调 Prompt，往往是人看了几个失败案例后补一句要求。GEPA 将其中一部分工作自动化：读取推理、工具调用与返回结果，反思失败原因，提出并测试 Prompt 修改，同时保留具有互补优势的候选。[GEPA 论文](https://arxiv.org/abs/2507.19457)

自然语言在这里既是指令，也是传递经验的媒介。一个“失败”分数只告诉系统结果不好；一段执行记录却可能说明，系统在工具报错后重复提交了相同参数。后一种信息更容易转化为具体修改。

例如，针对前面的 SQL 场景，可以提出这样一条候选规则：“如果估计行数与实际行数差异很大，先检查统计信息，再考虑强制索引。”这是说明机制的例子。它是否有效，要放回相应数据库与任务中观察，不能因为措辞专业就直接当成知识。

### Memory：让经验能够积累，也能够被修正

长期记忆涉及两个不同问题：**记住什么，以及以后何时把它取出来。**

Mem0 研究从持续对话中提取、整合、检索重要信息，并探索图结构记忆。它更接近为跨会话的事实与关系建立可维护的记忆系统。[Mem0 论文](https://arxiv.org/abs/2504.19413)

ACE 则把上下文视为不断更新的行动手册：执行产生轨迹，反思提炼策略，整理过程将策略增量写回。它关注反复重写整份上下文时，具体经验逐渐被概括掉的问题，因此采用结构化、局部更新的方式保留细节。[ACE 论文](https://arxiv.org/abs/2510.04618)

两者提示了一个实用区别。记住“这个仓库使用什么构建命令”，与记住“遇到哪类失败应按什么顺序定位”，都可以帮助 Agent，但需要的组织方式并不相同。前者偏事实，后者偏操作经验。

进一步看，记忆的寿命也需要管理。仓库升级后，旧命令可能失效；原本有效的规避方法，可能只是绕过了一个已经修复的缺陷。让记忆持续更新，需要保留它的适用条件，并能用新证据修正旧内容。

### Tool / Skill：让经验变成可以直接调用的动作

当相同步骤反复出现，经验可以从文字变成程序。

Voyager 在 Minecraft 中维护可复用的代码技能库，将已经掌握的行为用于后续探索。技能使后面的任务能够从更高层次开始组合，而不必每次从基础动作重新写起。[Voyager 论文](https://arxiv.org/abs/2305.16291)

Alita 将这条思路扩展到外部工具：识别能力缺口，搜索开源资源，生成与调试工具，配置环境，再把有用的能力封装成可复用的 MCP 服务。模型因而能在解决任务时扩展自己的工具集合。[Alita 论文](https://arxiv.org/abs/2505.20286)

这里可以用一个工程上的区分：Tool 提供具体动作接口；Skill 描述一组动作在什么条件下、按什么步骤完成一类任务。不同系统的命名会有差异，但二者都能承载经验。

比如，查询优化 Agent 写出一个“采集执行计划并对比关键变化”的工具，又整理出一份“慢查询诊断”的技能。前者减少机械操作，后者组织判断顺序。下一次任务的起点便发生了变化。

不过，写出脚本只是能力形成的一步。它还需要能被发现、正确调用，并在依赖变化后继续维护。技能库的价值取决于后续使用，而不是目录里累计了多少文件。

### DeepSeek Harness：把可改造范围打开到运行系统

DeepSeek Harness 的开发者预览把模型、工具、技能、会话、执行循环等能力放进插件体系，由 Cordis 管理装载、卸载与依赖。官方提供的 Creator mode 支持查看当前运行时、在内存中试验插件，并组合新的运行模式；会话事件流则记录模型实际看见的输入和工具交互。[DeepSeek Harness 官方介绍](https://www.deepseek.com/harness/en/)

这类设计为自进化提供了一个直接的接口：Agent 可以从编写业务产物，走到创建和调整自己的工作部件。Code mode 中，多步工具操作还可以由模型生成的 TypeScript 程序组织起来。

需要准确定位这项能力：官方展示的是**可检查、可组合、可扩展的运行基础设施**；要成为自动自进化系统，还需要接上提出修改、检验效果和选择版本的过程。

从工程角度推演，一条可能的路线是：发现重复失败 → 定位相关插件或流程 → 在隔离运行中试验修改 → 比较后续任务表现 → 保留合适的版本。具体源码结构可继续读本站的 [DeepSeek Harness 源码阅读](/posts/deepseek-harness-source-reading/)。

## Harness 的更深处：流程、框架，以及改进器本身

### 工作流：谁先做、谁复核、谁与谁交流，也能搜索

很多 Agent 系统把“规划—执行—审查”写成固定流程。但同一套流程可能让简单任务多绕几圈，却给复杂任务留下过少的验证时间。

AFlow 把工作流表示成代码：节点调用模型，连接关系表达执行逻辑，再通过蒙特卡洛树搜索与执行反馈探索改动。ADAS 的 Meta Agent Search 更直接地让元 Agent 编写新的 Agent 程序，并参考已有设计档案继续搜索。[AFlow](https://arxiv.org/abs/2410.10762)、[ADAS](https://arxiv.org/abs/2408.08435)

优化对象因此可以包括：增加哪种角色、在哪一步调用工具、是否并行尝试、失败后怎样回退。设计空间已经超出单段 Prompt。

另一个方向是让不同经验各有去处。EEVEE 面对混合任务流，为不同任务簇分配 Prompt 配置，并交替更新路由器与 Prompt，缓解不同任务之间的干扰。它说明自进化可以产生分工，而不必把所有经验不断塞进同一份总指令。[EEVEE 论文](https://arxiv.org/abs/2606.11182)

### 框架：Agent 修改自己的源代码

Darwin Gödel Machine（DGM）让编码 Agent 修改自身代码，并用编码基准检验生成的版本。系统维护多个 Agent 变体的档案，从已有版本继续探索，形成分叉的演化路径；论文报告的改进涉及编辑工具、长上下文管理和同行复核机制。[DGM 论文](https://arxiv.org/abs/2505.22954)

这里的“自修改”很具体：被编辑的仓库包含 Agent 的运行逻辑。一个更好的文件编辑接口，可能同时帮助它完成用户任务，以及继续修改自己的实现。

也正因如此，保留多个版本有意义。某个版本暂时不是总分最高，却可能提供另一种有用的工作机制。进化式搜索允许从不同分支继续前进，减少所有尝试都被当前最佳方案约束的情况。

### 改进器：连“怎样寻找下一次改进”也可以变

再向上一层，就会遇到 STOP：先有一个调用语言模型、按效用函数改进输入程序的改进器，再把改进器自己的代码交给它优化。论文观察到的策略包括束搜索、遗传算法与模拟退火；模型权重在这个过程中保持不变。[STOP 论文](https://arxiv.org/abs/2310.02304)

Hyperagents 则将完成任务的 Agent 与负责修改的元 Agent 放进同一个可编辑程序，使元层的修改机制也成为优化对象。研究关注的已经包含“产生新 Agent 的过程怎样积累改进”。[Hyperagents 论文](https://arxiv.org/abs/2603.19461)

可以用三个问题辨认它们的区别：

1. 当前程序怎样做得更好？
2. 负责完成任务的 Agent 怎样做得更好？
3. 负责改进 Agent 的程序怎样做得更好？

递归关系由此出现。但“可递归修改”只说明系统开放了更深的搜索空间；是否持续获得收益，还取决于模型能提出什么改动，以及反馈能否选出有效的改动。

## 第三条路线：Model 自进化，让经验进入参数

前面的 Agent 即使换了工具、记忆和流程，底层模型也可能完全没变。模型层的学习则通过训练改变生成分布：同样的输入下，某些回答或动作变得更容易产生。

难点随之转移：**训练信号从哪里来？**

人不可能为所有新任务编写标准解题过程。自训练、强化学习、自博弈、测试时学习，分别尝试降低对这些人工示范的依赖。它们用到的信号却很不一样。

### 强化学习：从结果奖励中学习怎样行动

对于有可验证结果的任务，可以让模型尝试多条轨迹，再根据结果更新策略。数学答案是否正确、代码能否通过测试，都可以提供奖励；训练者无需逐字规定推理过程应该长什么样。

DeepSeek-R1 系列中的 R1-Zero 展示了直接通过强化学习激励推理行为的路线。这里省去的是预先提供人工推理轨迹的要求，正确性奖励仍然发挥关键作用；完整 R1 训练流程也不能等同于只有这一个阶段。[DeepSeek-R1 原始报告](https://arxiv.org/abs/2501.12948v1)

因此，将 RL 放进自进化地图，是因为 Agent 的尝试可以成为下一轮训练材料。一次交互中出现“让我检查一下”，是推理行为；多次尝试经奖励反馈改变后续行为倾向，才涉及参数学习。

### 自训练与 TTRL：没有答案时，利用已有模型的判断

一种朴素的自训练方式，是让模型生成候选答案，筛选后作为训练目标。它借用了模型已经拥有的能力，也会继承模型的偏差：错误的伪标签被反复学习，可能让错误更加稳定。

TTRL 研究没有显式标签的数据：通过多次采样和多数投票等方式估计奖励，再进行强化学习。它利用的是预训练模型已有的先验，把测试时的计算投入接到参数更新上。[TTRL 论文](https://arxiv.org/abs/2504.16084)

多数一致之所以可能有用，是因为模型并非随机猜测；但一致性也不等于事实正确。这条路线最值得关注的地方，是如何从不完美的信号中获得净收益，而不是把模型的置信当作金标准。

### 自博弈：让模型参与产生下一轮训练问题

自博弈不一定是两个聊天机器人互相辩论。它可以让不同版本的模型互为训练对手，也可以让出题与解题两个角色相互推动。

SPIN 从经过监督微调的模型出发，让旧版本生成回答，再训练模型区分这些回答与已有的人类示范。它不需要每一轮追加新的人工标注，但仍使用原有示范数据作为参照。[SPIN 论文](https://arxiv.org/abs/2401.01335)

Absolute Zero Reasoner（AZR）进一步让同一模型承担出题和解题：生成能够促进自身学习的代码推理任务，再通过代码执行器检查任务与答案，为训练提供可验证奖励。论文所说的零外部数据针对这一训练阶段，系统仍建立在预训练模型与执行环境之上。[Absolute Zero 论文](https://arxiv.org/abs/2505.03335)

这两种做法的差别很清楚：SPIN 继续挖掘已有示范的学习价值；AZR 尝试同时扩展训练课程与解题能力。

出题端也需要合适的激励。如果总出已经会做的题，训练缺少新信息；如果总出无法验证或远超当前能力的题，又很难得到有效反馈。**题目分布怎样跟着能力变化，是自博弈的一部分。**

### Test-time Training：在读取输入时更新快速状态

“测试时学习”还有架构层的含义。Test-Time Training（TTT）的一类序列层把隐藏状态表示为小型可学习模型，读取序列时用自监督学习更新它；TTT-Linear 与 TTT-MLP 是其中两种实例。[TTT layers 论文](https://arxiv.org/abs/2407.04620)

这个机制与“对整个模型做一轮新训练”不同：被快速更新的状态可以只服务于当前序列，是否跨任务保留取决于具体设计。它也与 TTRL 的奖励驱动更新属于不同层面的做法。

读到一个系统宣称“推理时也在学习”，可以进一步看三个细节：它更新的是文本上下文、快速状态，还是持久权重？更新依据是什么？任务结束后，这些变化保存在哪里？这些信息比名称本身更能说明能力如何延续。

## 三条路线怎样接起来：一次经验的多种去向

三类对象并非互斥。一段生成的代码，作为任务输出时是 Artifact；被注册为下次可调用的工具时，进入 Harness；其执行轨迹被筛选为训练数据后，又可能影响 Model。分类取决于它在系统里承担的角色。

SIA 是联合更新的一项研究：Feedback-Agent 根据任务反馈推动 Harness 和模型权重的调整，尝试连接通常分开研究的两条路线。论文在三个任务域中报告了联合更新优于只迭代 Harness 的结果；这些实验支持继续研究协同更新，尚不能据此认定任意 Agent 都会获得同样的收益。[SIA 论文](https://arxiv.org/abs/2605.27276)

![一次经验的四种去向：保留候选产物、沉淀记忆和工具、积累训练样本、改进搜索机制；分别服务于后续搜索、执行、训练和改进过程](/images/posts/agent-self-evolution/experience-paths.svg)

*同一次成功无需写入所有层。该保留什么，取决于经验的复用范围和更新成本。*

回到 SQL 的假设，可以构造一条具体的协同路线：

- **当前任务**：试验几种查询写法，留下正确且更快的版本。
- **任务结束**：提取适用条件明确的诊断经验，补充执行计划比较工具。
- **积累一批任务后**：筛选高质量轨迹，用来训练模型对查询结构和执行反馈的判断。
- **反复改进后**：检查搜索过程本身，调整何时并行试验、何时停止、怎样挑选候选。

这是一个设计示例。它展示了不同更新可以采用不同节奏：文本和工具通常更容易局部修改，权重更新则需要训练资源、样本组织和整体行为检查。把所有学习都塞进一次实时循环，未必经济。

## 看一个自进化系统，沿着“变化”往下追

读完这些路线，再看新项目时，可以用一张简短的表定位它：

| 想弄清的问题 | 要找的具体信息 |
| --- | --- |
| 什么在变？ | 候选产物、Prompt、记忆、工具、流程、源代码、权重或快速状态 |
| 依据什么变？ | 执行结果、人工反馈、模型评价、伪标签、规则奖励、对手产生的任务 |
| 变化怎样留下来？ | 版本档案、技能库、持久记忆、部署配置、模型 checkpoint |
| 下一次怎样用到？ | 检索、调用、路由、加载新版本、使用更新后的策略 |
| 改进花了多少代价？ | 搜索与训练开销、运行成本、失败候选，以及新任务上的收益 |

这也能解释为什么“跑了很久”“写了很多记忆”“自改了很多次”都只是过程信息。不同路线要展示不同的结果：产物搜索展示候选质量，Harness 改进展示后续任务表现，模型学习展示更新后的能力与迁移。

**Agent 自进化正在扩展可被经验改变的范围。** 这些对象涵盖答案和代码、经验手册、工具与工作流程，也包括模型参数，以及产生改进的机制。真正值得追踪的，是这些变化怎样在下一轮工作中发挥作用，并进一步创造新的学习机会。
