一个 Agent 能把美国航空 2013 年的员工数据算成一份报告，说明检索、计算和生成已经串起来；它是否接近上线条件，则要看四条边界能否连成闭环：副作用在哪里被拦截，人工决定如何写回状态，一次运行怎样被追踪，版本怎样经过评估后再发布。

这篇文章把课程中的演示按这条控制链重排。它讨论的是视频已经展示的机制和仍需补测的条件，不把 Demo 直接等同于生产可靠性。

## 这个视频系列在做什么

这是一套 39 集、总时长约 12 小时 22 分钟的 Bilibili 课程。前面从 LangChain 基础、RAG、数据库 Agent、结构化抽取、文本分类一路讲到长文档摘要；和 Agent 上线直接相关的内容，集中在三组演示：

- 财务分析 Agent：读取财务报告，检索数据，计算员工结构，再由 Review Agent 复核；
- 银行助手和订单助手：处理个人信息、退款、转账、冻结账户等带副作用的动作；
- 追踪、评估和扩展：用 Langfuse 展开一次运行，保存提示词版本，再把在线执行交给 Gateway、Worker 和评估 Worker。

标题强调 LangGraph 和 MCP；从转录看，贯穿这些演示的主线是：模型可以自由生成下一步动作，系统怎样把这种自由限制在可检查、可恢复的范围内。

## 先看答案背后的执行链

财务 Agent 接收的问题是：从美国航空 2013 年的财务报告中找出六类员工人数，计算占比，再生成报告。演示里，一个 Agent 负责从 PDF 数据中检索和计算，另一个 Review Agent 重新核对人数、总数和比例。

用户最后只看到一段报告。报告背后至少发生了文档读取、检索、计算和复核。任何一步出错，最终文本都很难告诉你错误从哪里开始。

这也是 Agent 和普通问答程序的分界线：上线时要保存整条执行链，包括这句话经过的模型、工具、状态和版本。

把这条链展开，大致是：

~~~text
用户输入 → 输入检查 → Agent 决策 → 检索或工具调用
                         ↓
                    高风险动作审批
                         ↓
             状态恢复 → 结果复核 → 输出检查
~~~

![Agent 从输入检查到评估发布的控制链手绘图](/images/posts/agent-production-readiness/agent-control-chain-handdrawn.png)

*图：从输入检查到评估发布的 Agent 控制链。*

每个节点的失败处理都不同。输入命中规则时应该结束请求；工具参数需要人工确认时应该暂停并保存状态；审批完成后应该从原位置继续；模型或工具报错时应该留下可定位的 Trace。把这些情况都交给最后一个模型自行解释，系统就无法区分“拒绝”“重试”和“已经产生副作用”。

## 一、把副作用挡在工具边界外

安全演示没有设置一个笼统的“安全开关”，而是把检查点放在执行链的不同位置。

| 检查位置 | 视频中的处理 | 直接控制的风险 |
| --- | --- | --- |
| 输入进入模型前 | 命中“暴力”“毒品”等关键词后返回固定提示 | 恶意或不合规请求进入模型和工具链 |
| 模型调用前、工具返回后 | 检测邮箱、银行卡号等个人信息，按规则替换、保留末四位、哈希或报错 | 敏感信息进入模型，或被工具结果带回回答 |
| 工具执行前 | 查询订单直接放行；退款、转账、冻结账户进入批准、拒绝或参数编辑 | Agent 在没有确认的情况下产生副作用 |
| 最终输出前 | 检查医疗、投资等内容，命中规则后替换成固定回复 | 不合规建议直接展示给用户 |

这四个检查点的顺序决定了它们各自能控制什么。输入检查越靠前，越容易阻止不合规请求进入模型；个人信息检查需要覆盖模型调用前和工具返回后，因为数据可能在工具查询之后重新出现；高风险审批必须发生在副作用之前；输出检查负责最后一道内容边界，但它无法撤销已经完成的转账或写库。

演示中的动作可以按风险分成三类：

| 风险级别 | 例子 | 执行策略 |
| --- | --- | --- |
| 低风险 | 查询订单、读取数据 | 自动执行，记录参数和结果 |
| 高风险 | 退款、转账、冻结账户 | 执行前暂停，等待批准、拒绝或编辑参数 |
| 内容风险 | 医疗建议、投资建议、个人信息 | 在模型输入、工具结果或最终输出处检查 |

这里有一个容易混淆的边界：工具权限解决“谁可以调用”，Guardrail 解决“输入、参数、结果和输出是否符合规则”。前者限制能力，后者检查运行时内容。

数据库 Agent 把这个原则落到了工具约束上。演示中的规则包括先查看表和表结构、默认最多返回 10 条、只允许查询，以及查询报错后重新生成语句。一次 SQL 执行因为尾部的分号报错，换成工具 Agent 后，错误被当作观察结果，模型据此重新组织查询。

这个失败比“模型会不会写 SQL”更有价值。模型能提出一条语句，和系统允许它执行这条语句，是两层不同的控制。只在提示词里写“只能查询”可以减少误操作，数据库账号的只读权限才是阻止越权写入的硬边界。

## 二、人工审批的核心是状态写回

退款演示里有一个很具体的 bug。

用户先要求退款订单 001。人工审批节点把参数改成 002，但 Agent 仍然反复确认 001。审批界面里的参数已经变了，后续模型读取到的事实却没有变。

视频后续在提示词中补充了一条规则：如果工具参数发生变化，说明人工已经介入修改，后续直接按新参数执行。修改后，Agent 按 002 完成退款，并在回复中说明实际处理的订单。

这个例子说明，人工介入至少要完成四步：

1. 保存原始工具名和参数，生成待审批状态；
2. 保存人工的批准、拒绝、理由或参数编辑；
3. 把编辑后的结果写回后续执行节点；
4. 让最终回复引用实际执行的参数。

如果把这四步落成一个状态对象，至少要能区分原始参数、有效参数、审批动作、操作者、理由和当前执行状态。原始参数用于审计，编辑后的参数用于执行，审批理由用于解释拒绝或修改，当前状态用于中断恢复。直接覆盖原始参数会让后续审计无法回答“用户最初要求了什么，人工改了什么”。

人工审批还涉及重复执行。用户刷新页面、SSE 连接断开或网关重试时，系统需要根据请求标识和审批状态判断这次操作是否已经执行。视频主要展示了中断、批准、拒绝和参数编辑；断线重连、重复提交和多用户并发恢复属于上线时要补上的状态测试。

流程停在“等待批准”并不等于审批生效。审批组件、模型上下文和工具执行如果各自维护一份状态，用户在界面里改了订单，系统仍可能执行旧意图。

会话历史也是同一个问题。在历史感知检索演示中，用户先问“任务分解是什么”，再追问“它有哪些方法”。检索器要先结合历史，把追问改写成独立问题，再去查文档。换一个会话，代词失去指向，系统就应该按当前上下文重新处理。

因此，thread_id 或 session_id 定义的是消息、文件、检索上下文、审批状态和短期记忆的隔离边界。中断恢复时，恢复的也应该是这份状态。

## 三、让最终答案变成一条 Trace

普通界面只显示财务报告。接入自托管 Langfuse 后，一次运行被展开成一棵 Trace 树：模型调用、工具调用、Review Agent、自定义业务步骤和状态变化都挂在同一个请求下面。

这棵树至少可以分成五层：

| 层级 | 记录什么 | 排查时回答的问题 |
| --- | --- | --- |
| Trace | 用户、会话、输入、最终输出、版本、Trace ID | 这是哪一次完整请求 |
| Generation | 模型、提示词、输入输出、Token、耗时、错误 | 哪次模型调用改变了结果 |
| Tool / Observation | 工具名、参数、权限、结果、耗时、错误和重试 | Agent 实际调用了什么 |
| Span | 自定义业务步骤、父子关系、状态和业务标签 | 哪一段业务流程花了时间 |
| Event | 中断、审批、拒绝、回退和状态变化 | 请求在什么时候改变了路径 |

只有把父子关系和状态事件保存下来，日志才会变成 Trace。单独记录一堆模型输出和工具日志，仍然无法回答“这次答案对应哪一次工具结果”。

视频展示的记录包括用户、会话、版本和 Trace ID，也包括每次模型调用的输入输出、模型、Token、耗时，以及工具名称、参数、结果、错误和重试。这样排查成本或延迟时，可以沿着父子关系找到具体是哪次调用产生了资源消耗。

一次 Trace 页面显示了 7,163 个输入 Token、6,400 个输出 Token、6.53 秒的模型调用耗时，成本字段为 0.006369。这组数值在演示中的作用，是把资源消耗挂回一次执行链，让读者知道成本和延迟可以沿父子关系定位到具体调用。

提示词也被放进了同一条链路。视频演示了在 Langfuse 中保存提示词、设置发布标签，运行时按标签读取线上版本；平台不可用时，代码回退到本地提示词。提示词修改因此有了版本、运行记录和回退位置，后续可以和评估结果放在一起比较。

对于 Agent 来说，Trace 的价值不只是监控。它把“答案错了”拆成了可定位的问题：检索错了，工具选错了，参数错了，模型算错了，还是某次重试改变了结果。

## 四、评估要成为发布闸门

视频给出的评估流程可以压缩成四个动作：

1. 写清业务规则和标准答案；
2. 准备正常、失败和人工修正后的样本；
3. 针对具体 Trace 做人工标注；
4. 由独立的评估 Worker 或评估模型批量判断。

一条可用的评估样本至少要把输入、期望答案或业务规则、实际输出、Trace ID、人工标签、错误类型、模型版本和提示词版本放在一起。否则评估结果只能告诉你“这次分数低”，无法回到具体执行步骤，也无法判断低分来自检索、工具参数还是最终生成。

评估模型负责执行判断，业务标准仍然由人定义。财务 Agent 至少要检查员工总数、占比公式和引用报告是否匹配；工具 Agent 还要检查工具选择、参数和拒绝后是否产生了副作用。

提示词改动后，评估对象也要跟着版本走：答案质量、工具行为、耗时和 Token 一起比较。线上新出现的失败 Trace，应该进入下一轮回归样本，替代聊天窗口里的手工重试。

结构化分类演示补上了一个细节：模型返回 JSON，业务约束仍然可能是松的。初次分类时，标签和值域没有完全收敛；把标签改成枚举、把分值范围写进数据模型后，输出才有明确的可接受集合。

这条经验同样适用于工具参数。模型提出计划，枚举、范围、只读权限和审批策略负责把计划限制在可执行集合里。

## 五、在线执行和评估执行要拆开

视频后半段给出了一套作者设计的并发架构：负载均衡器把请求分给多个 SSE Gateway，Gateway 把任务写入 Redis 队列；Agent Worker 负责模型和工具执行，完成后把 SSE 事件送回网关；PostgreSQL 保存会话、检查点、记忆和 Trace 映射；评估请求进入另一条队列，由评估 Worker 异步处理。

请求路径可以画成这样：

~~~text
用户请求 → 负载均衡 → SSE Gateway → Redis 队列 → Agent Worker
                                      ↓              ↓
                               请求状态/Trace      模型与工具
                                      ↓              ↓
                         SSE Gateway ← 执行结果 ← PostgreSQL

评估样本/失败 Trace → 评估队列 → 评估 Worker → 评分与回归结果
~~~

Gateway 和 Worker 分开后，长连接的生命周期与模型调用的生命周期可以分别处理。Gateway 负责把事件持续推给浏览器，Worker 可以在后台等待模型、工具或人工审批；评估任务走独立队列，批量评分时不会占满在线请求的执行槽位。

这套拆分的关键不在组件数量，而在职责边界：

- Gateway 维护长连接和流式事件；
- Agent Worker 承担可能阻塞的模型与工具调用；
- 评估 Worker 处理回归任务，不占用在线回答的执行资源；
- 共享数据库不等于共享数据，文件、记忆、审批状态和 Trace 仍要按用户和会话过滤。

作者用约 200、2,000、200 万的乘法例子解释 Worker 横向扩展。这个例子帮助读者理解“请求数增长后复制执行单元”的架构关系；真正决定能否上线的，是队列等待、并发数、P95 延迟、超时和恢复时间。

共享 PostgreSQL 也不等于完成了租户隔离。Worker 从数据库取回会话、文件、记忆或 Trace 时，必须同时带上用户和会话条件；审批状态也要和同一份恢复标识绑定。否则 Agent Worker 虽然被横向复制了，数据边界仍然可能在共享存储层被打穿。

## 从 Demo 到上线，还要补一张验收表

视频把关键机制跑通了，生产验收还需要把它们变成可检查的条件：

| 验收项 | 最小通过条件 |
| --- | --- |
| 可追踪 | 任意一次失败都能由 Trace ID 定位到模型、工具、检索或状态步骤 |
| 可评估 | 有固定样本、业务规则、人工抽检记录和版本对照 |
| 可恢复 | 工具超时、拒绝、中断或连接断开后，流程能够继续或安全结束 |
| 可隔离 | 多用户不能读取彼此的文件、记忆、检索结果和审批状态 |
| 可控成本 | 能按模型、用户和版本统计 Token、延迟和成本 |
| 可回滚 | 提示词、模型或 Schema 版本可切换，回归下降时能阻断发布 |

这张表把“安全可控”拆成了操作条件。比如“可恢复”不能只看代码里有没有 checkpoint，还要实际注入超时和断线；“可评估”也不能只看评估模型返回了分数，还要能找到对应的样本、规则和人工修正。

## 演示把哪些失败变成了可处理状态

这组演示实际跑通了几类变化：

- 违规输入在进入模型前被拦截，邮箱等个人信息在链路中被脱敏；
- 查询订单可以直接完成，退款可以批准、拒绝并填写理由，人工改过参数后按新参数执行；
- 转账、冻结账户等高风险动作进入人工确认，投资建议在最终输出阶段接受合规检查；
- 财务 Agent 的检索和计算结果可以由 Review Agent 复核，Trace 页面可以展开模型、工具和业务步骤；
- 提示词能够按版本读取，失败 Trace 可以进入人工标注和后续评估。

视频给出的数字分属三种用途：九千多条财务原始记录说明演示输入规模；一次 Trace 中的 7,163 / 6,400 Token、6.53 秒和 0.006369 说明单次运行的资源消耗；约 200、2,000、200 万用于解释 Worker 的扩展模型。

能用于效果比较的数据，视频没有提供：准确率、任务成功率、工具参数正确率、误拦截率、人工审批率、平均成本、P50/P95 延迟，以及提示词修改前后的评估对照都没有出现。系列标题中的“90%”同样没有统计口径，线上指标仍需来自独立评估。

## 结论：上线的是一条控制链

从这些演示可以得到一个工程判断：Agent 上线前要交付一条能拦截、暂停、恢复、追踪和回归的控制链。

动作边界决定什么可以自动执行，状态边界决定人工修改是否真正生效，Trace 决定错误能否定位，评估闸门决定版本能否继续发布。四者缺一个，系统就会在不同位置留下无法解释的空白。

视频展示了这些机制如何在 Demo 中运行。接下来仍需用真实权限、真实流量和故障注入验证多用户隔离、断线重连、重复提交、超时恢复和灰度回滚；这些属于上线验收，演示画面只说明控制链已经能够运行。
