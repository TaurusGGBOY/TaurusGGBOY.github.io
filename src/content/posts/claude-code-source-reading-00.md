2026 年 3 月 31 日早上，大量开发者只执行了一次普通的 `npm install`，拿到的却不只是编译后的 CLI，`cli.js.map` 里还带着可以逐条还原的 TypeScript 文本。不到两个小时，源码地址被公开，随后出现撤包、GitHub 镜像清理和借"泄露版 Claude Code"传播窃密木马的攻击。

这篇导读是源码解读系列的第 00 篇，也是一张读者地图，先讲清楚源码从哪里来（泄露时间线），再建立读代码需要的两个概念（Harness Engineering 与证据分层），最后给出三条学习路线和整系列的结构。读完它，你可以直接进入第 01 篇开始读源码。

先把边界说清楚，避免期望错位。这一系列专门拆解 Claude Code 的构建方式和工程取舍。它不承担使用教程或官方文档的职责，也不把本仓库的还原目录当作 Anthropic 内部仓库的原始组织。读者有 TypeScript/JavaScript 基础，了解 LLM API 调用和基本 git 操作，就可以跟着往下读。

## 核心结论

- **这是一次发布事故。** `@anthropic-ai/claude-code@2.1.88` 的 `cli.js.map` 携带了 4756 份非空 `sourcesContent`，把完整 TypeScript 源码文本放进了公开发布物；现有材料没有支持 Anthropic 内网被入侵的证据。
- **Claude Code 的主体是 Harness。** 社区估算约 1.6% 的代码属于 AI 决策逻辑，其余 98.4% 用于工具调度、权限、上下文、恢复与持久化。整个系列读的就是这部分工程代码。
- **一个发布工件把四个环节串成了事故链**，构建系统把源码写进 source map，npm 公开分发，社交平台和 GitHub 让源码快速复制，攻击者又利用事件热度包装恶意下载。撤包无法让事情恢复原状。
- **公开证据有明确边界**，源码传播和恶意利用可以追踪，但模型权重、用户数据或 Anthropic API 失守均未被现有证据证明。
- **判断结论可信度要用证据分层**，官方表述（Tier A）、静态源码（Tier B）、重建解释（Tier C）强度不同，本系列每篇都会标清。

## 阅读前需要建立的三个概念

在进入时间线和源码之前，先建立三个贯穿全系列的概念。它们把时间线和后面的源码阅读接在一起，**先问发布物暴露了什么，再问源码能证明什么，最后才讨论外部分析推导出的风险**。

- **Agent harness**，围绕模型组织上下文、工具、权限、状态与恢复的运行时。系列关注的源码主体正是这一层。模型负责推理，Harness 负责执行，工具怎么调度、命令能不能跑、历史怎么恢复，全都在这一层。
- **source map 的源码载荷**，`sources` 记录映射目标，`sourcesContent` 可以直接携带对应源码文本。泄露边界取决于发布物实际包含的字段，只有路径时只能恢复映射关系，保存完整文本时则能按条目还原源码。
- **证据层级**，发布物、官方文档与运行结果提供不同强度的证据。后续文章会把可确认事实、源码推断和外部分析分开标注（详见"证据分层"一节）。

source map 的结构并不神秘。它本质是一个 JSON 文件，`sources` 是文件路径数组，`sourcesContent` 与之一一对应，

```json [source]
{
  "version": 3,
  "sources": ["../src/query.ts", "../src/cli.tsx"],
  "sourcesContent": ["/* 源码全文 */", "/* 源码全文 */"],
  "mappings": "AAAA;AACA;..."
}
```

`mappings` 是压缩后的行/列映射（Base64 VLQ），负责把打包代码的每个位置指回源码位置；而 `sourcesContent` 直接把文本带进了发布物。2.1.88 的 map 两个字段都齐了，这正是泄露成立的原因。

## Harness Engineering｜Claude Code 的真正主体

读这套源码之前，先纠正一个常见误解，Claude Code 的竞争力不在模型，而在包裹模型的工程基础设施。

为什么从 Harness 而不是模型开始读？因为模型部分在公开源码里几乎不存在，源码里能看到的是模型调用、提示词组装和流式解析，而不是模型本身。你在这套源码里能读到的最有价值的东西，恰恰是那些"看起来不起眼"的部分，一条工具调用怎样通过权限、沙箱、回滚和恢复变成可靠操作，一次长会话怎样在压缩后还记得项目状态。**模型决定一个 Agent 能想多远，Harness 决定它能不能安全地走到那一步**。

把 Claude Code 想象成一辆车，**模型是发动机**，决定动力上限；但决定驾驶体验和安全性的，是底盘、转向、刹车、仪表盘和导航，这些就是 **Harness**。再换个比喻，**模型像一颗 CPU**，Harness 是主板、操作系统、内存管理和设备驱动。CPU 再强，没有外围系统和调度，也无法构成一台可用的计算机。

在 Claude Code 里，Harness 具体包括，工具调度、权限控制、上下文管理、记忆系统、任务规划、多 Agent 协作、安全沙箱、配置管理与状态恢复。用一张图概括，

```
┌──────────────────────────────────────────────────────┐
│                    Claude Code                        │
│                                                      │
│   ┌───────────┐    ┌──────────────────────────────┐   │
│   │   Model   │    │          Harness              │   │
│   │           │    │                               │   │
│   │  Claude   │◄──►│  工具调度 · 权限控制          │   │
│   │  Sonnet   │    │  上下文管理 · 记忆系统        │   │
│   │  Opus     │    │  任务规划 · 多 Agent 协作     │   │
│   │           │    │  安全沙箱 · 配置管理          │   │
│   └───────────┘    └──────────────────────────────┘   │
│     ~1% 代码量            ~99% 代码量                 │
└──────────────────────────────────────────────────────┘
```

系列沿用的比例是，模型约占 1% 的代码量，Harness 约占 99%。社区对 2.1.88 的估算更精确地说是约 **1.6% 的 AI 决策逻辑与 98.4% 的运营基础设施**，但这个数字的证据等级是 Tier C，统计口径有争议，见下文"证据分层"。

Harness 里最重要的一类工作是 **Context Engineering**，决定模型"看到什么"。它只有四件事，

| 策略 | 干什么 | 系列对应章节 |
|，-----|，-----|，-----|
| **Write（写入）** | 系统提示词、CLAUDE.md、项目指令如何分块组装 | 16 |
| **Select（选择）** | 什么内容进模型、什么只给摘要（如 ToolSearch 只暴露工具名而不暴露完整 Schema） | 15、09 |
| **Compress（压缩）** | 长会话放不下之后，token 估算、microcompact、partial/full compact 与摘要回填 | 17 |
| **Isolate（隔离）** | subagent 在隔离上下文中执行，只回传摘要 | 24 |

这套框架是整个系列的阅读主轴，每读到一段代码，先问它在 Harness 的哪个位置，再问它对模型输入做了什么。四个策略在 2.1.88 里都有对应的具体实现，

- **Write**，系统提示词被拆成多个块，按用户、项目、环境分层；嵌套目录的 CLAUDE.md 采用延迟加载，只有进入对应目录才注入。
- **Select**，`ToolSearch` 只向模型暴露工具名而不是完整 Schema；单工具结果有预算限制；subagent 只向父 Agent 返回摘要，这些都在压缩之前就减少了上下文占用。
- **Compress**，token 估算决定何时触发 microcompact 或 partial/full compact；压缩后会重新注入文件附件、plan mode 指令和 skill 附件，确保模型在压缩后仍知道当前项目状态，且每一步都受 feature gate 控制。
- **Isolate**，Task 运行时与 Subagent 机制在独立上下文中执行委派任务，模型、工具与结果回流都有明确边界，主 Agent 只拿到摘要而非全部过程。

第 17 篇会看到最完整的压缩实现（五层压缩、feature gate 控制），第 48 篇会把它总结成"策划和维护最优 token 集"这一层工程。记住一句话定位，**Context Engineering 决定什么内容该进、该砍、何时注入**。

## 源码泄露时间线

![source map 如何暴露 Agent harness 的证据链](/images/posts/claude-code-source-reading-00/00-series-guide-detail-handdrawn.png)

这篇导读追踪的是一个发布工件怎样把构建、分发、复制和社会工程串成事故链。可确认的起点在 npm 包，原本只服务调试的 source map 把源码文本带进了公开发布物。

先说明本节的证据方法，方便你自己复核。时间线里所有数字都来自两类来源，**一手发布物**（npm registry 的版本元数据、`cli.js.map` 的文件内容，本仓库保存了原始 tarball，可逐字节验证）和**公开报道**（媒体、安全公司报告与官方博客，正文均给出来源链接）。报道之间数字口径不同（如 8100 与 8000+）时，两者都保留并注明差异来源。按时间顺序，事故是这样展开的。

### 起点｜2026-03-30 22｜36｜48 UTC，一次 npm publish

[npm registry](https://registry.npmjs.org/@anthropic-ai%2fclaude-code) 记录的发布时间是 2026 年 3 月 30 日 22，36，48 UTC，换成北京时间是 3 月 31 日 06，36。`@anthropic-ai/claude-code@2.1.88` 在这个时间进入公共仓库。

包里同时出现了 `cli.js` 和 `cli.js.map`。前者是打包后的程序，后者负责把打包代码映射回源文件。source map 存在的本意是调试，开发者工具需要知道打包代码的每一行对应源码的哪一行，因此发布物带上 map 是常见做法，问题不在"带没带 map"，而在 map 里**带没带 `sourcesContent`**。按上一节的概念，泄露边界由 `sourcesContent` 决定，只有文件路径时只能恢复映射关系，保存完整文本时则能按条目还原源码。2.1.88 属于后者。

本仓库检查了原始发布物中的 `cli.js.map`，

```text [source]
cli.js.map 检查结果（@anthropic-ai/claude-code@2.1.88）
├── 文件大小：59,766,257 字节
├── sources 条目：4756 个
└── sourcesContent：4756 份，均为非空文本
```

这个 map 同时告诉调试器源码文件名和对应文本。拿到 npm 包以后，**不需要反编译 `cli.js`**，按数组位置把路径和内容配对，就能恢复出可阅读的源码树，这正是本仓库 `restored-src/` 的来源。

> 一些外部报道把泄露规模写成约 51.2 万行代码、1900 个 TypeScript 文件，本仓库恢复出的 map 条目是 4756 个。差异来自统计口径，1900 更接近业务源码文件数，4756 还包含第三方依赖和生成内容。决定能否恢复源码的条件是每一项 `sources` 都有对应的非空 `sourcesContent`。

### 08｜23｜从发布错误变成公开事件

包发布不到两个小时，安全研究者 Chaofan Shou 在 [X 上公开了这个问题](https://x.com/Fried_rice/status/2038894956459290963)。帖子指出 Claude Code 的源码通过 npm 中的 map 文件暴露，还给出了 Anthropic Cloudflare R2 上的源码压缩包地址。这个帖子到现在显示约 **3573 万次浏览**。

泄露过程可以简化成一条链路，

```
Anthropic 发布 npm 包 → 包内 map 暴露源码文本 → 研究者公开可直接下载的地址 → 其他人开始保存和镜像
       发布流程问题                发布流程问题                传播阶段开始             不可逆传播
```

前两步属于发布流程问题，后两步则让它进入不可逆的传播阶段。3573 万次浏览的意义就在这里，它说明这波流量足够大，大到复制行为不可能被单个撤包动作追回。关闭 R2 链接或删除 npm 版本，只能阻止新的用户继续从原地址下载；已经保存到本地、同步到 GitHub 或重新打包的副本仍会留在其他分发节点，因此处理重点很快从"修包"转向"清理副本"。

### 当天｜撤回版本，再处理 GitHub 镜像

Anthropic 随后撤下了 2.1.88。今天查看 npm registry，仍然可以看到这个版本的发布时间，但相邻版本都有的 tarball 地址、完整性签名和文件统计已经不存在。对用户来说，"撤下"意味着新安装者拿不到这个版本，但已经装好的用户如果执行更新，会带着被弃用的版本继续运行，这也解释了为什么紧随其后的 issue 反馈会集中在功能失效上。一个公开的 [Claude Code issue](https://github.com/anthropics/claude-code/issues/41666) 也把 2.1.88 称为 yanked release，并记录了 Skills、MCP 和自定义命令失效等用户反馈。

这里要区分两个故障机制，**源码泄露触发立即撤回**，**Skills 和 MCP 失效属于版本质量问题**。它们共同暴露了同一条发布链路的风险，自动更新先分发功能异常版本，随后该版本又因源码暴露被撤下。

撤包之后，Anthropic 同一天向 GitHub 提交了 [DMCA 下架通知](https://github.com/github/dmca/blob/master/2026/03/2026-03-31-anthropic.md)。通知确认这批代码的版权属于 Anthropic，并要求删除主要镜像及其 fork。GitHub 在文档顶部说明，目标仓库网络超过 100 个，而且 Anthropic 认为大部分 fork 与源仓库存在相同侵权，因此平台最初对包含 **8100 个仓库**的整个网络执行了处理。

这个动作说明了两个事实，第一，**公开可下载只描述传播状态，代码许可仍由原版权约束**；第二，npm 撤包只能处理发布源，已经扩散到其他平台的副本需要继续通过版权程序清理。

### 4 月 1 日至 2 日｜技术事故影响扩大

[《华尔街日报》4 月 1 日的报道](https://www.wsj.com/tech/ai/anthropic-races-to-contain-leak-of-code-behind-claude-ai-agent-4bc5acc7)称，Anthropic 最初的请求让 GitHub 移除了 8000 多份副本和改编版本，随后又把范围**缩小到 96 个**，因为第一次处理影响了超出预期的 GitHub 账户。对开发者社区来说，被误伤的账户很可能只是 fork 了某个镜像仓库，并没有恶意；而对 Anthropic 来说，这变成了一道两难，撤得太慢，副本继续扩散；撤得太快，误伤扩大。DMCA 快速压缩了主要镜像网络，却产生了新的问题，清理范围过大。影响至此已超出工程团队内部的打包错误，进入平台治理和开发者关系层面。

4 月 2 日，[Business Insider](https://www.businessinsider.com/anthropic-copyright-infringement-claude-code-2026-4) 引述 Anthropic 发言人称，公司正在推出措施防止类似事件再次发生。报道还指出一个尴尬的背景，Anthropic 长期面对训练数据版权诉讼，这次却需要站在版权拥有者的位置，用 DMCA 阻止别人继续传播它的代码。一个 source map 配置问题，就这样被放进了 AI 公司如何对待他人作品和自身知识产权的讨论里。

不过，影响范围需要说清楚。这次暴露集中在 Claude Code 的**客户端 Agent harness**，涉及工具调用、权限、状态和宿主逻辑。[Zscaler 的安全分析](https://www.zscaler.com/blogs/security-research/anthropic-claude-code-leak)没有把模型权重、安全流水线和用户数据列入现有证据能够确认的暴露范围。换句话说，现有材料指向的是**"外壳"（Harness）**，不是模型权重。

### 4 月 3 日至 7 日｜下游风险落到仿冒仓库与窃密木马

源码撤回和 GitHub 镜像清理之后，风险仍沿着已经下载的副本、衍生分析与重新分发继续存在。

[Trend Micro 4 月 3 日的调查](https://www.trendmicro.com/en_gb/research/26/d/weaponizing-trust-claude-code-lures-and-github-release-payloads.html)发现，攻击者在公开披露后的 **24 小时内**建立了假冒的"Claude Code 泄露版"仓库。这些仓库声称提供无限制版本或解锁企业功能，下载内容实际包含 **Vidar 信息窃取程序**和 **GhostSocks 代理木马**。

攻击机制并不复杂，用户看到源码泄露新闻后，会主动搜索 GitHub 镜像；攻击者只需要准备一个名字相似的仓库、一份看起来像源码的 README，再把恶意可执行文件放进 Release 压缩包，就能利用这波搜索流量。Trend Micro 的判断是，这批攻击者原本就在轮换使用二十多个热门软件品牌，Claude Code 只是当时最容易吸引开发者的新诱饵。

到 4 月 7 日，[Trend Micro 的后续监测](https://www.trendmicro.com/en_gb/research/26/d/claude-code-remains-a-lure-what-defenders-should-do.html)仍把它标记为**活跃攻击**。被跟踪的仓库当时已经有 **838 个 star、1060 个 fork**，新的恶意压缩包确认下载 **533 次**，之前被替换或删除的链接还无法统计；后续样本又加入了 PureLog Stealer。

因此，泄露给 Anthropic 带来的安全影响分成了两层，

| 层面 | 内容 | 对应风险类型 |
|，-----|，-----|，-----|
| 源码本身 | 外部人员更容易研究 Agent 的攻击面 | 代码与架构风险 |
| 事件热度 | 给恶意软件提供可信的传播外壳 | 品牌与供应链风险 |

修复 npm 包只能解决前者的一部分，解决不了已经形成的搜索关键词和社会工程场景。

### 4 月 23 日｜官方复盘聚焦质量问题

4 月 23 日，Anthropic 发布了 [Claude Code 质量问题复盘](https://www.anthropic.com/engineering/april-23-postmortem)。文章承认 3 月到 4 月间有三项独立改动造成体验下降。其中，**3 月 26 日上线的一项缓存优化**会在会话空闲后反复清除旧 thinking，导致 Claude 遗忘上下文、重复执行，并造成更多缓存 miss。Anthropic 在 4 月 20 日前修复了这些问题，随后为所有订阅用户重置使用限额，还承诺让更多内部员工使用与用户完全相同的公共构建版本，并加强 Code Review、评测和渐进发布。

这篇复盘值得放进时间线，但它的证据范围只覆盖缓存问题与后续测试措施，**官方文章未建立缓存问题与 `cli.js.map` 发布之间的因果关系**，也未把后续措施描述为泄露事故专项修复。两件事发生在同一段发布周期，共同暴露了内部测试与公共发布之间的差距。对读者来说，这正是证据分层发挥作用的地方，复盘文章本身是 Tier A 材料，可以确认"Anthropic 承认了缓存问题、修复了并重置了限额"；但"缓存问题是否与泄露有关"没有任何一层的证据支持，只能作为未回答问题记录在案。

截至今天，Anthropic 的公开回应主要体现在 npm 撤包、GitHub DMCA，以及媒体转述的"正在采取措施防止再次发生"；公开材料尚未披露具体失效的构建规则、文件过滤配置或发布检查。也就是说，**事故的确切技术根因（哪条构建规则没生效）至今没有官方口径**，本系列后续所有关于发布流程的讨论，都在这个证据边界内进行。

### 7 月 16 日｜这次泄露到底留下了什么

npm registry 当前的 `latest` 是 **2.1.211**，`stable` 是 **2.1.204**，说明 Claude Code 在泄露后继续发布版本。2.1.211 的 npm 包只有 **7 个文件，解包大小约 160 KB**；泄露前的 2.1.87 则有 **19 个文件，解包后约 46.6 MB**，对照之下，"包里不再有完整源码"的痕迹相当明显。注意这里没有把 2.1.88 与其他版本的行为混在一起，后续版本的文件数只能说明发布物形态，不能反推 2.1.88 的内部结构，这正是本系列要回避的"版本混读"。

### 事故链总结

回到开头的问题，一个 source map 为什么能产生持续几个月的影响？因为它打通了四个原本分开的环节，

1. **构建系统**把源码写进 map（发布前）；
2. **npm** 把 map 公开分发（发布时）；
3. **社交平台和 GitHub** 让源码快速复制（发布后数小时到数天）；
4. **攻击者**利用事件热度包装恶意下载（发布后 24 小时内出现）。

任何一个环节单独看都不复杂，连起来以后，撤回一个 npm 版本就不可能让事情恢复原状。

四个环节还对应四类不同的"修复"，构建环节的修复是配置层面（过滤 `sourcesContent`）；分发环节的修复是流程层面（发布检查）；复制环节的修复只能靠版权程序（DMCA）；利用环节的修复则需要安全响应与社区教育（识别仿冒仓库）。前三类属于 Anthropic 可以控制的工程问题，第四类取决于攻击者与用户行为，这解释了为什么事件"收尾"后几个月仍有余波。

到今天，可以确认的直接影响是，Anthropic 撤回了正式版本，处理了大规模 GitHub 镜像，公开承诺防止重演，并承受了版权、发布质量和品牌安全方面的压力。公开证据的覆盖范围止于客户端源码及其传播处置，**尚不足以证明 Claude 模型权重、用户数据或 Anthropic API 失守，也不足以计算收入损失或客户流失**。

研究这次事件时，最重要的边界是把三件事分开，**公开发布事故可以确认，源码传播和恶意利用可以追踪，Anthropic 内部损失只能在有证据时讨论**。

## 证据分层｜怎样判断一个结论可信

源码泄露事件里充斥着二手报道和社区猜测。公开文章引述的每个数字（8100 个仓库还是 96 个、4756 个条目还是 1900 个文件）背后都有不同的统计口径，不先建立证据分层，读这套源码很容易被"看起来权威"的表述带着走。为了不把猜测当事实，本系列把结论分成三个证据层，每篇文章都会标注，

| 层级 | 名称 | 来源 | 强度 |
|，-----|，-----|，-----|，-----|
| **Tier A** | product-documented | Anthropic 官方文档、工程文章、公开表述 | 说明产品公开强调了什么，不能代替实现证据 |
| **Tier B** | code-verified | 2.1.88 静态源码中的文件、函数、参数、分支与默认值 | 对"代码实际怎么走"是最强证据 |
| **Tier C** | reconstructed | 社区分析、跨系统比较、基于代码模式建立的架构解释 | 把分散实现连成系统模型，确定性低于直接源码事实 |

用一个例子说明分层如何工作。本仓库的知识图谱可以确认，`queryLoop()` 位于 `restored-src/src/query.ts`，返回 `AsyncGenerator`，接收 `QueryParams` 和已经消费的 command UUID，并连接消息、模型、工具、压缩、恢复与状态模块，这是 **Tier B**，可以写成源码事实，

```ts [source]
// restored-src/src/query.ts（2.1.88）
// queryLoop(): AsyncGenerator<AgentEvent, void, QueryParams>
// 连接消息、模型、工具、压缩、恢复与状态模块
```

而"Claude Code 让模型保留局部行动选择，同时用密集的确定性 harness 管理工具、权限、上下文、恢复和持久化"这类系统级判断，是把大量 Tier B 事实连成模型，属于 **Tier C**，确定性低于直接源码事实，但解释力更强。

回到本节的第一个例子，**1.6% AI 决策逻辑 / 98.4% 运营基础设施**来自社区估算，属于 **Tier C**，分类口径和可复现的逐文件数据均未给出，适合表达趋势，不能当作精确的软件度量。源码能够稳定支持的结论（Tier B）是，**权限、工具路由、上下文、恢复与持久化占据了主要实现面**。

配合证据分层，代码块统一使用四种标签，

- `[source]` ， 还原源码的直接片段（Tier B）
- `[pseudocode]` ， 按源码结构简化的示意（Tier B 边界内，非逐字）
- `[inference]` ， 根据调用关系推出的解释（Tier C）
- `[runtime]` ， 运行命令与实测输出（Tier B/C 之间）

读文章时这样应用这套分层，**看到 `[source]` 和 `[pseudocode]`，可以对照 `restored-src/` 自己验证**；看到 `[inference]`，先追问"这个结论依赖哪些调用关系、缺了哪一环会变"；看到 `[runtime]`，可以复制命令在本地复现。文章里的陈述性文字同样分层，能回到源码文件的句子是 Tier B，来自官方文档的表述是 Tier A，把多个事实连成系统模型的段落是 Tier C。

同时要诚实面对这套方法的边界，**本系列不能回答什么**，

- **模型权重与内部行为**，公开物是客户端 Harness，权重、训练细节与 API 内部实现不在证据范围内；
- **Anthropic 内部组织方式**，还原路径是构建时记录，不等于团队目录结构；
- **其他版本的行为**，官方文档的最新描述、2.1.204/2.1.211 的行为，都不能与 2.1.88 混读；
- **需要运行证据的问题**，静态源码无法确定真实运行时行为，只能标为推断（`[inference]`）或列入已知缺口。

## 三条学习路线

三条路线共享同一个起点（00），之后按目的分叉。选择建议，**只有两三个小时**，走速览路线，先把主干跑通，其余章节以后按需补；**有完整的一周预算**，走完整路线，48 篇按序推进，每篇结束都可以停下来写一段"这一篇让我新理解了哪个机制"；**带着具体工作问题**（比如"我要给我的 Agent 加权限控制"），走主题专项，先读对应的三到四篇再回到主线。

| 路线 | 时间 | 章节 | 适合谁 |
|，-----|，-----|，-----|，-----|
| **速览路线** | 2到3 小时 | 00 → 01 → 02 → 06 → 17 | 想快速理解核心架构与请求主线 |
| **完整路线** | 3到5 天 | 00 → 01 → 02 → … → 48 | 想系统掌握全部子系统 |
| **主题专项** | 每条半天 | 安全，12 → 13 → 14 → 18；上下文，16 → 17 → 19 → 40；多 Agent，23 → 24 → 25 → 26 | 聚焦特定方向的开发者 |

**速览路线**只需两三个小时就能建立"一次请求如何走完 Claude Code"的心智模型，01 看全局地图，02 跟完一次请求，06 看循环如何推进，17 看长会话如何压缩，五篇覆盖了 Harness 的主干，读完能回答"一条 prompt 进来之后发生了什么"。**完整路线**按 S0到S5 顺序读完 48 篇，每篇相对上一篇只增加一个明确的心智模型模块，适合想系统掌握全部子系统的工程师；按每篇 20到40 分钟计算，3到5 天可以完成，中途可随时停下（每篇独立成文，不依赖上一篇的结论）。**主题专项**带具体问题来读，安全方向从权限引擎（12）一路读到沙箱（13）、文件（14）与 Hooks（18）；上下文方向从系统提示词（16）读到压缩（17）、错误恢复（19）与会话记忆（40）；多 Agent 方向从 Task 运行时（23）读到 Subagent（24）、Teams（25）与 Plan Mode（26）。

无论选哪条路线，推荐顺序都是从 01 开始而不是从某一篇"感兴趣的"开始，01 建立的架构坐标会让后续每篇少走弯路，就像读地图之前先看指北针。

## 系列架构概览

![Claude Code 源码解读系列路线图](/images/posts/claude-code-source-reading-00/series-roadmap.png)

这一篇 00 先解决"源码从哪里来"的问题。接下来 47 篇不按目录顺序逐个介绍文件，而是**沿着一次请求的执行过程向外展开**，先建立系统模型，再进入 Agent 内核，然后补齐安全、上下文、扩展、宿主和产品能力。

编号规则，`XX` 表示顺序而非源码目录层级，`00-a` 是插在 00 之后的进阶文章（论文解读）。文件名使用稳定的英文 slug，中文标题统一采用 `Claude Code源码解读XX：解释` 格式，后续每篇正文第一行都与本文件标题格式保持一致，方便你在菜单和正文之间互相定位。

| 阶段 | 章节 | 一句话主题 |
|，-----|，-----|，-----|
| **S0** 阅读边界与全景 | 00到01 | 源码从哪里来、全局架构图长什么样 |
| **S1** Agent 执行内核 | 02到09 | 一条请求如何进入 QueryEngine 与 Agent Query Loop，消息、流式与工具如何运转 |
| **S2** 执行、安全与上下文 | 10到20 | 工具执行后系统怎样守住边界，权限、沙箱、文件、压缩、Hooks、错误与会话 |
| **S3** Agent 能力与扩展 | 21到30 | 能力怎样扩展到单个 Agent 之外，Command、Skill、Task、Subagent、Teams、MCP、插件 |
| **S4** 宿主、状态与分布式 | 31到39 | 同一内核怎样服务不同宿主，TUI、无头 SDK、配置、模型路由、远程与可观测性 |
| **S5** 产品化与实验 | 40到48 | 内核之上的产品能力，记忆、Buddy、Voice、MagicDocs、通知与系列总结 |

各阶段要点一览，

- **S0（00到01）**，00 是本文，解决"源码从哪里来、怎么读"；01 架构全景把 Claude Code 拆成入口、查询内核、执行与状态、扩展与远程运行几个部分，先建立坐标，避免看到函数名就猜整个系统的职责。
- **S1（02到09）**，从一次用户输入开始，02 请求链路跑通上下文组装、模型流、`tool_use`、工具结果到最终输出的主线；03 启动流程研究第一条请求到来之前的 CLI 入口与配置预取；04 比较交互式 CLI、print/headless、SDK、MCP server 等入口为何共享同一套内核；05到09 深入 QueryEngine、Agent Query Loop、消息模型、API 流式调用与 Tool 抽象。
- **S2（10到20）**，工具执行以后，系统怎样守住边界，10到11 讲工具调度与生命周期，12到13 讲权限引擎与 Bash 沙箱，14到15 讲文件与搜索工具，16到17 讲系统提示词与上下文压缩，18到20 讲 Hooks、错误恢复与会话历史。
- **S3（21到30）**，能力怎样扩展到单个 Agent 之外，Command、Skill、Task 运行时、Subagent、Agent Teams、Plan Mode 与 Worktree、MCP 集成、插件系统、LSP 与浏览器/IDE 适配。
- **S4（31到39）**，同一个内核怎样服务不同宿主，AppState 共享状态、Ink TUI、快捷键与 Vim、无头 SDK、配置与 Feature Flags、模型路由与认证、Bridge 与远程会话、可观测性、更新与迁移。
- **S5（40到48）**，Agent 内核之上的产品与实验能力，Session Memory、Memdir 团队记忆、AutoDream 后台整合、Assistant/KAIROS、Buddy 陪伴模式、Voice 语音、MagicDocs 与通知 Mailbox，最后 48 收束全系列并整理产品演进时间线。

每一篇都遵循同样的节奏，先用一个具体场景或问题开头，中间用带证据标签的代码块推进，结尾用"本篇新增机制"告诉你这一篇相对上一篇在心智模型里增加了什么，并留一个练习或问题衔接下一篇。第 02 篇开始会固定观察一张具体的支付工单，同一件事如何经过模型、工具、权限、状态和宿主，最终变成一次可恢复、可扩展的 Agent 执行，保证 48 篇讲的是同一套系统，而不是 48 个孤立的话题。

完整的逐篇索引见 [INDEX.md](./INDEX.md)。另外，[00-a 一篇逆向论文怎样拆开生产级 Agent](./00-a-dive-into-claude-code-paper.md) 基于同一份 2.1.88 公开源码解读学术论文，是证据分层方法的完整演示（论文先用 Tier A/B/C 区分公开意图、源码事实与重建解释，再提炼出 5 个价值、13 条原则、7 个高层组件和 5 层实现结构），建议读完 00 后作为进阶材料。

## 版本声明与阅读约定

**本系列只讨论 `@anthropic-ai/claude-code@2.1.88`**。这是泄露发生时唯一可以完整恢复源码的版本，其他版本（包括泄露后的 2.1.204、2.1.211）的行为与内部结构无从验证。这个限制保证了可复现性，**任何读者都可以下载同一个 tarball、运行同一个还原脚本、得到同一份 `restored-src/`**，然后逐行验证本系列的每一个 Tier B 结论。这也是源码解读与二手文章的区别。

所有源码引用都指向本仓库 `restored-src/` 下的还原文件，路径形如 `restored-src/src/query.ts`。还原目录按模块组织（`src/entrypoints/`、`src/query/`、`src/tools/` 等），但请注意，**路径是构建时记录的，不是 Anthropic 内部仓库的原始组织方式**，构建工具可能合并、重命名或移动文件，路径只能说明"这个文件被编译进哪个位置"。

还原目录的大致布局（只列后续文章会反复引用的部分，完整清单见 [source map 还原原理](./reference/source-map.md)），

```text [source]
restored-src/
├── src/
│   ├── entrypoints/    # CLI 入口、fast path 分流（cli.tsx、main.tsx）
│   ├── query/          # QueryEngine、queryLoop、消息与循环
│   ├── tools/          # 工具注册表、buildTool、基础工具池
│   ├── commands/       # prompt / local / local-jsx 命令
│   ├── skills/         # Skill 发现与加载
│   ├── tasks/          # Task 抽象、subagent 委派
│   ├── state/          # AppState、轻量 store
│   ├── hooks/          # PreToolUse / PostToolUse / Stop 等
│   ├── services/       # 模型路由、认证、更新等宿主服务
│   ├── ink/            # 终端渲染（自定义 Ink/React）
│   ├── vendor/         # 第三方与生成内容
│   └── ...（bootstrap、buddy、memdir、plugins、remote 等）
└── node_modules/
```

三条硬性约定，

1. **不把还原路径当成 Anthropic 内部仓库的原始组织方式**，source map 记录的是构建时路径，不等于团队目录结构。
2. **不混入其他版本**，官方文档的最新描述、其他版本的行为、外部文章的结论，都不与 2.1.88 源码事实混合；发生冲突时以本仓库源码为准。
3. **每个结论都标注证据层**，能由源码直接确认的写成事实（Tier B），调用关系连接的职责写成解释（Tier C 边缘），缺少运行证据的明确标成推断（`[inference]`）。

几个读者常问的问题，一并回答，

- **为什么不用最新版本做演示？** 因为 2.1.88 是唯一能完整恢复源码的版本，用它可以逐字验证；最新版本只有编译产物，结论无法复核。
- **为什么不去官方仓库读代码？** 官方仓库的公开代码与 2.1.88 的发布物可能不同步，且无法证明对应关系；本系列的一切结论都必须回溯到 `restored-src/`。
- **泄露后版本的文件更少，是不是说明 Anthropic 修复了？** 7 个文件与 19 个文件的差异是发布物形态的事实，但它如何构建、为何缩小，属于没有公开证据的问题，只能记入已知缺口，不能下结论。

## 练习｜用 10 分钟体验 Harness 的第一次优化

读第 01 篇之前，先亲手感受一个最小的 Harness 优化，**启动分流**。前提是你已经安装了 Claude Code（任意近期版本都可以做这个观察，它演示的是启动链路，与本系列的 2.1.88 源码对照时请记住"版本边界"）。在终端里依次执行，

```bash [runtime]
claude --version
```

```bash [runtime]
claude -p "hello"
```

两条命令的观感完全不同，`--version` 几乎瞬间返回；`claude -p "hello"` 要完成配置加载、上下文组装、模型调用才输出结果。这是因为 CLI 入口先检查参数，为 `--version` 这类命令保留 fast path，输出版本后立即返回，完整程序根本不加载；普通路径则使用动态 `import()`，所有特殊分支排除后才加载 `main.tsx`。进程启动早于完整 Claude Code 初始化。简化成示意就是这样，

```ts [pseudocode]
// restored-src/src/entrypoints/cli.tsx（2.1.88，结构示意）
if (args[0] === '--version' || args[0] === '-v' || args[0] === '-V') {
  // 输出版本，立即 return，完整 CLI 保持未加载
}
if (!isFastPath(args)) {
  await import('./main.tsx') // 只有这时才加载完整 Claude Code
}
```

观察点时留意三件事，**第一**，试试断网状态，`--version` 依然瞬间返回，因为它根本不走初始化链路，这是"fast path 不加载不需要的东西"最直观的运行证据；**第二**，`claude -p` 与交互式 REPL 虽然共享同一套内核，但 `-p` 是非交互模式，把 prompt 参数或 stdin 交给 Agent 执行后直接输出到 stdout，适合 Shell 管道、脚本和 CI（对应第 04 篇"运行模式"与第 34 篇"无头 SDK"）；**第三**，两条命令的差异可以记为一次"计时实验"，等读完第 03 篇，你就能在源码里找到决定这个差异的分支。

再往深一层，为什么启动不能写成一个大函数？因为这里同时有依赖、信任和响应速度三种约束，配置/cwd 决定能力装配，信任决定项目内容能否生效，`--version` 等 fast path 又不该加载完整 UI。分阶段初始化、动态 `import()` 和 effect 分别把三种约束落到代码里。这就是 Harness Engineering 的第一个实例，**不需要的能力不加载，不需要的状态不建立**，它也是第 03 篇"启动与引导"的主题。
