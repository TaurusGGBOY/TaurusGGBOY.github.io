如果在 2026 年 9 月启动一个新的 RAG 项目，我会先写下业务约束，准备带相关性标注的真实查询，再用三到四个候选组合跑同一条检索链路。

我的默认起点是：**中文私有化从 Qwen3-Embedding-0.6B + Qwen3-Reranker-0.6B 开始；国际托管文本检索从 Voyage 4 + Rerank 2.5 开始；截图和图表检索单独评估 Qwen3-VL。** 这三条路线对应不同的部署和输入条件，后文会给出升级、替换和不加重排的判断条件。

本文以 **2026 年 9 月 20 日查阅的官方文档与模型卡**为资料截点。参数和公开成绩来自对应来源；场景推荐是我的工程判断；示例预算与阈值是评测设计，均不代表我已经在同一业务数据集上实测了这些模型。目标是把“应该选谁”落实为能够验证、能够推翻的决定。

## 一、先分清两个模型分别负责什么

Embedding 把查询和文档编码成向量，使系统可以从大量文档里快速找出候选。Reranker 接收查询与候选文档，重新判断它们的相关性；它通常不需要和 Embedding 来自同一家厂商。

例如，一个知识库有一百万个片段。先用关键词和向量检索各取一批候选，融合后留下 50 条，再让 Reranker 排序，最终给回答模型 5 条。这里的 50 和 5 是实验起点，可以根据证据覆盖与延迟调整。[Sentence Transformers 的两阶段检索说明](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

如果正确文档根本没进入那 50 条，重排救不了这次查询；如果正确文档已经排第一，重排可能只增加延迟，甚至把它降下去。因此，选型必须分开回答两个问题：**有没有找全证据，以及有没有把最有用的证据排到前面。**

```text
查询 + 可访问范围
       ├── 关键词 / BM25 ──┐
       └── Embedding / ANN ┤
                          ↓
                  融合、去重、候选集
                          ↓
                  Reranker（可选）
                          ↓
                  证据片段 → 回答模型
```

访问范围需要在召回时约束两个通道，并在交给外部重排或回答服务前再次保证结果可访问。不能先把无权读取的正文发送出去，再靠最终答案过滤。

## 二、2026 年 9 月应该拿哪些模型来比

候选池应该覆盖不同的成本与部署路线。一上来测试二十多个相近型号，会消耗标注和部署时间；先筛掉不满足输入、许可、地域与服务预算的模型。

### Embedding：能力对比与入围理由

下表的窗口是模型或服务公布的输入上限，不是推荐切块大小。向量维度也不是质量等级。

| 候选 | 官方规格或能力 | 我会让它参加什么比较 |
| --- | --- | --- |
| Qwen3-Embedding-0.6B / 4B / 8B | 32K 输入；最大维度分别为 1024 / 2560 / 4096；支持可变维度与任务指令 | 中文、多语言、自托管文本检索的主候选，先测 0.6B，再测扩大模型是否划算 |
| BGE-M3 | 8192 tokens、1024 维；支持 dense、sparse 和 multi-vector 三种检索表示 | 现有 BGE 系统的基线；需要比较多路召回时保留 |
| pplx-embed-v1-0.6B / 4B | 32K；1024 / 2560 维；另有 context 版本 | 大规模、自托管、量化索引，以及片段需要上文才能理解的场景 |
| Voyage 4 / 4-lite / 4-large | 32K；支持 256 / 512 / 1024 / 2048 维 | 托管文本检索中，比较平衡、低成本和质量优先三档 |
| Cohere Embed v4 | 128K；256 / 512 / 1024 / 1536 维；支持文本与图像混合输入 | 已有 Cohere 部署体系、企业多语言与文档检索 |

| Gemini Embedding 2 | 文本、图片、视频、音频、文档进入统一空间 | 已有 Google 技术栈，或者需要跨模态检索 |
| Qwen3-VL-Embedding-2B / 8B | 文本、图片、截图、视频及混合输入 | 自托管多模态检索；与纯文本路线分开评测 |

这张表刻意保留 BGE-M3：已有系统更换 Embedding，要付全量重算、双索引存储和灰度迁移的成本。一个新模型公开成绩更高，并不能单独证明值得迁移。

国内托管项目还要加入百炼的 `text-embedding-v4` 与当前文档列出的 `qwen3.7-text-embedding`。它们是服务型号，不能把开源 Qwen 权重的上下文、吞吐和价格直接套过去。例如，官方同步接口给 v4 的单条上限是 8192 tokens，而 qwen3.7 服务列为 128,000 tokens；还要按北京或新加坡等具体地域核对。对于已有 OpenAI 系统，保留 `text-embedding-3-small` 作为低改造成本的对照组。[百炼 Embedding 接口](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)、[OpenAI 模型页](https://developers.openai.com/api/docs/models/text-embedding-3-small)

### Reranker：先看部署方式，再看复杂度

| 候选 | 入围理由 | 影响选择的条件 |
| --- | --- | --- |
| Qwen3-Reranker-0.6B / 4B / 8B | 多语言、32K、可自定义指令；提供大小模型阶梯 | 用同一候选集衡量扩大模型的收益与 P95 代价 |
| bge-reranker-v2-m3 | 多语言的成熟自托管基线 | 已有服务先保留，重点测长输入截断与关键业务题 |

| Cohere rerank-v4.0-pro / fast | 明确区分复杂任务与低延迟、高吞吐路线 | 按部署平台、文档长度和实际账单比较 |
| Jina reranker-v3.5 | 0.6B 的 listwise 路线，一次联合处理候选列表 | 需要测试候选顺序、列表长度和许可条件 |
| zerank-2 | 开放权重的另一个重排对照，模型卡标 Apache-2.0 | 在自己的语言与领域切片上评测，不能由英文结果外推中文 |
| Qwen3-VL-Reranker-2B / 8B | 可以直接处理多模态查询与候选 | 只有正文包含视觉证据时才值得走这条链路 |

来源：[Qwen3 Reranker](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)、[BGE Reranker](https://huggingface.co/BAAI/bge-reranker-v2-m3)、[Voyage Reranker](https://docs.voyageai.com/docs/reranker)、[Cohere Rerank](https://docs.cohere.com/docs/rerank)、[Jina v3.5](https://huggingface.co/jinaai/jina-reranker-v3.5)、[zerank-2](https://huggingface.co/zeroentropy/zerank-2-reranker)、[Qwen3-VL Reranker](https://huggingface.co/Qwen/Qwen3-VL-Reranker-2B)。

Jina v5-text-small 和 reranker-v3.5 的模型卡均标注 **CC BY-NC 4.0**，商业自托管需要另行解决授权；下载得到权重，不等于获得免费商用许可。Qwen3 文本系列标 Apache-2.0，BGE-M3 和上述 Perplexity Embedding 标 MIT。选择托管 API 时则另看对应服务条款与部署区域。

### 公开横评能告诉我们多少

可以引用同一协议下的比较，但要保留协议。Jina reranker-v3.5 模型卡给出了如下结果：以 `jina-embeddings-v5-text-small` 为第一阶段，统一 top-100，指标为 nDCG@10（%）。

| Reranker | BEIR | MIRACL |
| --- | ---: | ---: |
| Jina v3.5 | 63.20 | 74.11 |
| Qwen3 4B | 62.28 | 76.56 |
| Qwen3 0.6B | 56.94 | 67.12 |
| mxbai-rerank-large-v2 | 62.45 | 69.65 |

这份**发布方报告**足以说明不同测试集会给出不同排序；它不是本文复现实验，也不包含业务延迟和采购成本。即使在同一张表里，也不能从 BEIR 列的胜出推出所有多语言任务都更好。[原始表与测试协议](https://huggingface.co/jinaai/jina-reranker-v3.5)

Embedding 同样如此。MTEB 覆盖多种任务、语言和模态；做检索应优先看匹配业务的 retrieval 子集、数据集版本与评价协议，而不是拿聚类、分类等任务混在一起的总分替代检索表现。[MTEB 项目](https://github.com/embeddings-benchmark/mteb)

## 三、从需求到最终决定，完整流程怎么走

### 第一步：把约束写成一页表

在下载模型前，先填写这些信息：

| 维度 | 要回答的问题 |
| --- | --- |
| 输入 | 中文、英文、跨语言？代码、表格、扫描件还是纯文本？ |
| 数据边界 | 查询与候选正文能否发到外部服务？允许哪些区域？ |
| 规模 | 片段总量、每日新增量、更新频率、峰值 QPS 各是多少？ |
| 时延 | 检索阶段的端到端 P95 预算是多少？不是只看模型推理时间 |
| 目标 | 找到任意一段答案即可，还是必须覆盖多个必要证据？ |
| 资源 | CPU、小显存 GPU、已有推理集群，还是只接受托管 API？ |
| 经济性 | 月预算是否包含建库、索引、冗余、重排和迁移？ |

例如，“中文为主、少量英文、数据不出内网、已有 GPU、百万片段、检索 P95 目标 400ms”可以成为一份评测合同。400ms 是项目提出的目标，不能写成某个模型的性能事实。

### 第二步：建立真正能区分模型的测试集

建议先用约 300～500 条真实查询做第一轮。这是启动规模，不是统计充分性的保证。给高风险场景和稀有语言留出足够样本；有查询日志时按流量抽样，同时保留困难题的独立分组。

至少覆盖六类问题：普通问答、准确型号或错误码、否定与条件限制、跨语言、长文档中的局部证据，以及库内确实无答案的问题。多跳任务另标“必须共同出现的证据集合”。

例如，问题是“试用期员工能否申请异地办公”。正例应该提供适用对象和条件；“正式员工异地办公办法”可能语义极像，却不回答这个问题。这样的困难负例比随机抽一篇完全无关的文章更有区分力。

每个样例记录查询、语言、业务类型、文档 ID、文档版本和相关性标签。我会采用 0～3 级：0 为无关，1 为主题相关，2 为部分支持，3 为直接支持。等级定义要给标注者具体例子。

标注池取 BM25、多个 Embedding 和现有系统的候选并集，再人工补找漏掉的证据。只标某一个模型的 top-10，会偏向它。未标注文档也不能自动视为已确认无关；公布指标时说明标注覆盖范围。

把调参用的开发集和最终盲测集隔开，同一原始文档、同一个问题的改写尽量分在同一侧，防止近重复泄漏。LLM 可以辅助初标，模型意见分歧和关键题仍需人工复核。

### 第三步：先测召回，把索引误差和模型误差分开

固定解析、切块、标题拼接、去重和语料版本，比较以下四条基线：

1. BM25。
2. 当前 Embedding 或一个低成本 Embedding。
3. 新 Embedding。
4. BM25 + 新 Embedding，使用 RRF 等方法融合。

“固定输入”指相同的业务信息，不意味着抹掉模型要求的 query/document 前缀。应为每个模型使用官方推荐的输入方式，再记录配置。否则测到的可能只是某个候选被错误调用。

对抽样语料先跑精确向量搜索，再比较 ANN。如果精确搜索能找到相关文档而 ANN 丢了，优先检查索引参数；如果精确搜索也找不到，才继续检查语义表示、切块与查询理解。**ANN Recall 是对精确近邻的还原程度，业务 Recall 是对相关证据的覆盖程度，两者不能混用。**

第一阶段看 Recall@20、Recall@50、Recall@100。先固定二值相关的口径，例如标签 ≥2，并对所有候选保持一致。Recall 定义为“前 K 个结果中相关文档数 / 标注相关文档总数”，还要报告 Hit@K，即至少命中一个相关文档的查询比例。无答案查询不适用前述召回分母，单独评估错误接受率。

如果业务必须同时找到退款规则和地区例外，仅命中其中一个不能算任务完成，再补充“必要证据集合完整覆盖率”。

### 第四步：固定候选集，单独测 Reranker

先冻结每个查询的候选 ID、原文和版本，让每个 Reranker 看完全相同的 50 条候选；保留“不重排”的顺序作为对照。这一轮测出排序器的独立贡献。

看 nDCG@5 / @10、MRR@10 和证据覆盖。nDCG 适合前面的分级标签；MRR 衡量首个相关结果的位置，使用前需固定“相关”是标签 ≥2 还是仅标签 3。所有模型用同一阈值定义，不能按结果好看与否临时改。

然后把入围 Reranker 接到前两名召回链路上，再做端到端交叉实验。例如两条召回链路乘以“不重排、轻量重排、较大重排”三档，共六个组合。**固定候选比较回答谁更会排序，真实链路比较回答最后系统该用谁。**

有些 listwise 模型会联合读取整批文档，需要增加候选顺序扰动和长列表测试。对于所有模型，都要统计把原本正确 top-1 降下去的次数，而不只是平均分增加多少。

### 第五步：用真实负载测延迟和成本

用相同硬件、精度、服务框架、输入长度分布和并发目标比较自托管候选；记录冷启动、预热、动态批处理、队列等待、网络传输、超时和重试。API 则从实际部署区域发请求。

测试候选数 20 / 50 / 100 和几档片段长度，输出质量—P95—成本曲线。一个模型单请求很快，在并发下排队严重，仍然可能不适合线上。

**`top_n=5` 通常只决定返回 5 条，不代表只计算 5 条。** 送入 100 条后再取 5 条，计算和计费仍可能覆盖全部候选。Voyage 的文档明确按 query 重复次数与文档 tokens 合计计算输入。[Voyage Rerank API](https://docs.voyageai.com/reference/reranker-api)

最终还要固定回答模型、提示词与证据预算，检查答案正确性、引用是否支持结论、无答案时能否拒答。检索分数提高而最终答案没改善，就需要看生成与证据拼接，而不是直接扩容检索模型。

### 第六步：按预先约定的规则选赢家

可以采用这样的决策顺序：先满足数据边界与许可，再满足关键题质量、P95 和失败率要求；在合格组合中，选择质量达到目标且总成本最低的一个。

提升幅度要用成对查询比较，并给 bootstrap 置信区间或至少报告逐题胜、平、负。不要因为 300 条查询上多答对两题就宣称全面领先；也不要让大量简单题掩盖某种语言或关键业务的退化。

如果团队希望设定“nDCG@10 至少增加 0.02 才接受额外重排成本”，应在实验前明确这是 **0～1 标度上的绝对增量**，并说明其业务依据。它不是通用行业门槛。

## 四、费用到底怎么算：一个可以复算的例子

假设一百万个片段，每片段平均 500 tokens。首次入库共 5 亿 tokens。按查阅时 Voyage 标准价格，不计免费额度和批量折扣：

| Embedding | 每百万 tokens | 首次向量化计算费 |
| --- | ---: | ---: |
| voyage-4-lite | \$0.02 | \$10 |
| voyage-4 | \$0.06 | \$30 |
| voyage-4-large | \$0.12 | \$60 |

这是模型 API 计算费，不含数据库、索引、解析、网络和日常新增文档。价格来源与口径：[Voyage 价格页](https://docs.voyageai.com/docs/pricing)。

接下来，假设每月一百万次查询，每次重排 50 个片段；查询平均 40 tokens，片段平均 500 tokens。按 Voyage 的计费方式，每次输入为：

```text
50 × 40 + 50 × 500 = 27,000 tokens
```

每月就是 270 亿 tokens。`rerank-2.5` 按每百万 \$0.05 计算，约 **\$1,350/月**；lite 按 \$0.02 计算，约 **\$540/月**。减少候选数、缩短无用正文或让一部分确定性查询绕过重排，都可能比节省首次建库的几十美元更重要。这是输入假设下的费用推算，不是吞吐或效果实测。

向量存储也要单列。一百万条、1024 维、float32 的原始向量约 **4.096GB（十进制）**；4096 维是 16.384GB。HNSW 图、元数据、正文、副本与迁移时的双索引另算。将向量降维或量化后必须重新测召回；模型权重量化节省的 GPU 内存，与索引向量量化节省的存储，是两件不同的事。

自托管则按“GPU 或 CPU 实例 + 空闲冗余 + 索引服务 + 运维 + 迁移”核算月成本。不要把权重体积当作推理显存需求，也不要把开源等同于线上计算免费。

## 五、不同场景，我最后会怎么选

下面给出的是**基于公开能力与部署约束的默认选型**。在拿到业务实测前，我会用它们开工；若未通过前面的盲测与性能目标，就按最后一列替换。BM25 和权限过滤是链路组件，不属于表中的模型二选一。

| 场景 | 默认 Embedding | 默认 Reranker | 选择理由与替换条件 |
| --- | --- | --- | --- |
| 中文为主、内网知识库、已有 GPU | Qwen3-Embedding-0.6B | Qwen3-Reranker-0.6B | 起步资源较小，便于建立完整基线；召回漏证据才测试 4B Embedding，候选已覆盖但排错才测试 4B Reranker |
| 已在生产使用 BGE，效果已达目标 | 保留 BGE-M3 | 保留 bge-reranker-v2-m3 | 用 Qwen3 / pplx 作挑战者；收益不足以覆盖重建成本时不迁移 |
| 国际托管、通用文本 RAG | voyage-4 | rerank-2.5 | 使用明确文本检索接口，先平衡质量和成本；质量优先加测 4-large，成本优先换 lite 并复测 |
| 国内云上托管、主要中文 | text-embedding-v4 | qwen3-rerank | 先建立区域可用的基线；将 qwen3.7-text-embedding / qwen3.7-text-rerank 加入同地域对照，满足增益与延迟条件再替换 |
| 已在 Cohere 或其云集成体系内 | embed-v4.0 | rerank-v4.0-fast | 优先减少集成与采购变化；复杂题排序仍不足且预算允许时换 pro |

| 大量依赖上下文的长文档片段，自托管 | pplx-embed-context-v1-0.6B 用于文档，配套 pplx-embed-v1-0.6B 用于查询 | Qwen3-Reranker-0.6B | 先验证上下文编码是否减少“片段脱离原文”的漏召回；实现复杂度不划算时回到标题+章节前缀的普通切块 |
| 截图、图表、扫描页，自托管 | Qwen3-VL-Embedding-2B | Qwen3-VL-Reranker-2B | 让检索与重排都能看视觉证据；只有质量增益足够才升级 8B |
| Google 体系、多模态托管 | gemini-embedding-2 | 先不加通用文本重排 | 保留原始模态评估；需要重排时接能读取候选模态的模型，不能用只看 OCR 的结果代表视觉重排 |

国内服务型号与接口以[百炼排序文档](https://help.aliyun.com/zh/model-studio/text-rerank-api)和[向量文档](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)为准。表中的代码模型见 [Voyage 当前型号](https://docs.voyageai.com/docs/embeddings)；context 系列的文档/查询职责见 [Perplexity context 模型说明](https://huggingface.co/perplexity-ai/pplx-embed-context-v1-0.6b)。

还需要单独说清楚三个取舍。

**质量优先不等于两个模型都选最大。** 如果 0.6B 召回已经覆盖必要证据，而 4B 重排改善了排序，把预算放在重排可能更合适；若候选里一直没有答案，反过来升级重排就是花错地方。

**Jina 值得进入挑战组，但商业自托管不能跳过授权条件。** 若已经使用 Elastic/Jina 服务，或已解决商业授权，`jina-embeddings-v5-text-small + jina-reranker-v3.5` 是值得与默认小模型组合正面对比的一组。公开表中有竞争力，不等于可以忽略自己的语言分布、输入协议和许可。

**金融与法律不因模型名字包含行业词就自动胜出。** 可以把 `voyage-finance-2`、`voyage-law-2` 加入领域对照，但最终看时间有效性、例外条款、数值单位、否定条件和来源引用。通用模型与领域模型应在同一批困难题上竞争。[Voyage 领域型号](https://docs.voyageai.com/docs/embeddings)

## 六、上线前最容易踩的五个坑

**第一，query 和 document 的输入协议错了。** Cohere 区分 `search_query` 与 `search_document`；Qwen3 需要按模型卡处理指令与池化；Gemini Embedding 2 的任务指令格式也不能照搬 Embedding 1 的 `task_type` 参数。先做小规模调用核对，再跑大批评测。[Cohere 示例](https://docs.cohere.com/docs/rag-complete-example)、[Gemini 任务格式](https://ai.google.dev/gemini-api/docs/embeddings)

**第二，把最大窗口当成最优切块长度。** 一份合同可以放进模型，不意味着压成一个向量后仍能稳定找到其中的短例外条款。先比较结构化切块、标题与章节前缀，再判断是否需要 context embedding 或整页视觉表示。

**第三，用统一的 0.5 阈值判断所有模型“有答案”。** 重排分数不是跨模型可比的概率；经过 sigmoid 也不自动获得校准。拒答阈值要在包含无答案查询的开发集上校准，模型或输入方式变化后重新验证。

**第四，重排阶段丢了上下文或模态。** 召回靠图片找到某张图表，重排却只看文件名；或者召回片段带着标题，重排时只传正文。此时上下游实际比较的不是同一份证据。

**第五，切换 Embedding 时只改了查询端。** 默认情况下，新的查询向量不能直接搜索旧模型的文档向量，即使维度一致。迁移要建立新索引、补齐增量、让查询模型与索引成对切换，再灰度验证和回滚。只有厂商明确声明兼容的模型组合才能例外，例如 Voyage 对其 4 系列给出了共享空间说明；仍需保持维度等设置一致并验证业务效果。[Voyage 兼容说明](https://docs.voyageai.com/docs/embeddings)

## 七、把选型结论写成一份能执行的记录

最终交付不应该只有“选 Qwen”或“选 Voyage”。至少记录模型 ID 与版本、向量维度、query/document 指令、切块规则、索引配置、候选数、重排输入长度、输出数量、部署硬件或区域，以及对应评测集版本。

再附一张结果表：每个组合的 Recall@50、nDCG@10、关键题覆盖、无答案错误接受率、P95、失败率和月成本；旁边写清楚为什么接受它，以及在什么条件下改选。

如果今天就要开工，我会从场景表的默认组合开始，用一套固定的真实查询找出第一个瓶颈：**漏召回，就修召回；排序差，就比较重排；证据齐全但回答错，就检查生成；质量达标但费用或延迟过高，就缩小模型、候选集或调用范围。** 每一步都能对应到数据，选型才真正结束。
