假设你要做一个助手：读取本次发布的变更，生成给用户看的版本说明。你可以直接把材料交给模型，也可以拆成整理、写作、审核几个步骤，还可以安排几个 Agent 分头调查。

同一个需求，为什么能画出这么多架构？要判断该怎么选，先看一个具体位置：**一次调用结束后，谁决定下一步做什么？**

Anthropic 的 [《Building effective agents》](https://www.anthropic.com/engineering/building-effective-agents) 从这个边界区分两类系统：Workflow 沿预先编写的代码路径执行；Agent 由模型动态决定执行过程和工具使用。文章发布于 2024 年 12 月 19 日。这里讨论它的架构分类，下面的版本说明案例是为解释这些模式构造的示例。

## 先把执行路径画出来

先把需求限制得很清楚：材料已经收齐，只需从中整理用户可见的变化。此时可以规定“提取变更 → 按影响分类 → 写成说明”。每个阶段都调用模型，但阶段顺序由程序决定。

再把需求改成“调查这次版本升级会影响哪些用户”。材料可能不齐：一条提交记录提到配置项被删除，助手需要继续查旧文档；另一条变更涉及接口行为，又要检查调用方。调查结果会改变后面的动作。

两种请求的差异落在路径上。前一种在运行前就能列出步骤，后一种需要根据新证据继续选择。模型调用次数相同，也可能对应不同的控制方式。

Anthropic 在 Workflow 部分列出五种常见模式，可以先用这张表定位：[原文工作流部分](https://www.anthropic.com/engineering/building-effective-agents)。

| 模式 | 调用之间怎样连接 |
| --- | --- |
| Prompt chaining | 按固定顺序传递上一步的结果 |
| Routing | 分类输入，交给相应分支 |
| Parallelization | 并行处理后聚合，包括分拆任务和多次判断 |
| Orchestrator-workers | 模型动态拆分子任务，委派后汇总 |
| Evaluator-optimizer | 生成与评价形成带反馈的循环 |

名字只说明结构。下面沿着版本说明这个例子，看每一种结构会改变什么。

## Prompt chaining：让中间结果承担明确职责

考虑一个自拟设计：第一步提取“变更、影响、来源”，第二步面向用户写作。如果提交记录写的是“修复重试时重复扣减配额”，第一步应保留触发条件，第二步才能解释哪些请求受影响。

这样拆分之后，中间表就是排查入口。如果最终稿把它写成“优化配额机制”，可以回头检查：第一步有没有丢掉“重试”这个条件？如果表里保留了，问题在写作阶段；如果已经丢了，就要修提取阶段。

串起来的收益在这个例子中很具体：两种错误可以分别定位。代价是后面的步骤依赖前面的产物。如果第一步把未经确认的推测写成事实，后面的文字越流畅，这个错误就越难被读者发现。

因此，我会先定义中间结果需要保留哪些证据，再决定是否值得多一次模型调用。

## Routing：分支收到的任务应当不同

现在假设变更里同时有用户功能和内部运维调整。用户功能要解释使用方式，运维调整要说明升级操作。可以先识别变更类型，再进入对应的写作分支。

这里容易遇到一个边界案例：删除旧配置项，既涉及运维，也会影响用户。若设计成只能选一个分支，信息就可能丢掉。这个示例可以允许一条变更命中两个类别，并在汇总时合并重复解释。

也就是说，路由设计要回答两个问题：分到哪一类，以及无法单独归类时怎么办。只测试明显的功能变更和明显的运维变更，看不出分类边界的问题。

## Parallelization：汇总者需要知道结果怎样合并

如果发布材料已经按客户端、服务端、命令行工具分好，可以让三个处理任务同时整理。它们各自返回结构相同的变更表，再由汇总步骤统一术语。这对应任务分拆。

另一种自拟设计是把同一份说明交给多个检查者，分别判断是否遗漏了不兼容变更。它们面对同一份材料，返回各自的判断。这对应多次判断。

这两种并行，汇总规则很不一样。前者合并内容时要去重；后者出现分歧时，要回到证据。假设两位检查者都说升级无影响，另一位指出旧参数已删除，汇总者需要核对参数变化，不能直接按人数把这条异议删掉。

从这个例子看，并行设计还需要一份汇总约定：哪些结果可以直接拼接，哪些冲突必须进一步核实。

## Orchestrator-workers：任务清单在运行时产生

前面的并行方案预先知道要检查三个组件。现在换成一个大型仓库，某次版本只改了客户端，另一次同时影响鉴权服务、SDK 和迁移文档。固定派出同样的任务，会让部分处理者无事可做，也可能漏掉新出现的模块。

可以让一个负责拆分的模型先阅读变更范围，再产生本次调查清单。例如，发现鉴权参数变化后，分别调查接口兼容性和 SDK 调用方式；没有涉及数据库，就不创建数据迁移任务。

在这个示例里，外层仍然可以写成“读取变更 → 拆分 → 执行 → 汇总”的固定协议，模型负责决定其中的任务清单。局部有模型决策，和整条执行路径交给模型，是两个不同的控制范围。

动态拆分带来的新问题是覆盖范围。汇总者需要检查“原始变更 → 调查任务 → 返回结论”能否对应起来。子任务全部完成，只说明已派出的工作做完了；一项变更如果在拆分时被漏掉，完成状态里不会自动出现它。

这也是我在这个例子里最关心的检查点：创建任务时保存它要解释哪条变更，收回结果时再对照。否则，一个组织得很整齐的团队也可能漏题。

## Evaluator-optimizer：反馈必须能指导下一次修改

最后，草稿已经生成，但一条升级说明没有交代替代配置。评价步骤可以返回具体意见：“你写了旧参数将被删除，请补充新的配置方式及其来源。”生成步骤带着这条反馈修订，再交回来检查。

若反馈只有“内容不够深入”，下一轮很可能只是增加篇幅。对这个版本说明任务，我会把评价要求限定为可检查的内容：不兼容变更有没有列出，迁移动作能否找到依据，正文有没有把内部实现写成用户承诺。

循环也要能够结束。材料里没有替代方案时，继续改写解决不了证据缺失。此时应把问题交回资料调查，或者在交付中保留待确认项。把“再写一轮”当作所有失败的处理方式，会掩盖不同的失败原因。

## 这五种工作流与 multi-agent 是什么关系

Anthropic 把上述五种模式列在 Workflow 下，随后单独讨论 Agent。它们描述的是调用如何组织，不能直接当成五种互斥的多 Agent 类别。[原文分类与组合说明](https://www.anthropic.com/engineering/building-effective-agents)

沿用发布说明的例子，同样一个“调查 SDK 兼容性”的 Worker，可以只接收材料、调用一次模型并返回表格；也可以持有独立上下文，自己查接口、读文档，再根据发现决定是否继续调查。外层都可以由 Orchestrator 委派，Worker 内部的控制方式却不同。

因此，读架构图时，我会分开检查两件事：

- 箭头：下一步固定串行、按类别分流、并行汇总，还是需要反馈后继续？
- 节点：只完成一次模型调用，还是自己维护任务状态、选择工具并持续执行？

原来常被放在同一张分类表里的名称，也可以按这个办法追问。看到 Supervisor，检查它能决定哪些任务；看到 Handoff，检查转交的是一次子任务，还是后续处理权。即使两个框架使用同一个名称，也要继续看实际交接了哪些状态。

## 用一份真实材料检查你的选择

可以取一次已经发布过的版本做小范围验证。先明确这份说明必须包含的变化，再分别检查：提取时有没有漏项，路由有没有把跨类别变更丢掉，并行汇总有没有吞掉分歧，动态拆分有没有覆盖全部材料。

如果单次调用已经能满足这些要求，就保留这个方案。需要增加步骤时，把原因落到一处可观察的失败上，比如“迁移条件在写作时被省略”，再检查新增的中间结果是否解决了它。

重新读 [《Building effective agents》](https://www.anthropic.com/engineering/building-effective-agents) 时，可以对照自己的流程，在每个节点旁写清输入、输出和下一步的决定者。这个动作完成后，哪些地方需要模型判断、哪些地方用固定流程就够，通常就更容易讨论了。
