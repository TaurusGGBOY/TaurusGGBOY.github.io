让一个智能体修改 VS Code 的设置：调试暂停时，把焦点留在调试控制台，别自动跳回编辑器。它可以打开设置页，搜索、滚动、点击；也可以先确认对应配置项，再修改 `settings.json`。

CUA-Universe 的论文给出了这道题的两条轨迹。纯 GUI 路径耗尽 60 次动作，任务失败；GUI+CLI 路径用了 5 次 CLI 调用和 12 次 GUI 动作，任务成功。后者在界面里定位设置，再把 `"debug.focusEditorOnBreak": false` 写入文件并检查持久化结果。这个例子把问题说得很具体：智能体需要知道哪一步适合看界面，哪一步适合直接改结构化状态。［[附录 J](https://arxiv.org/html/2609.05374v1#A10)］

上海交通大学与浙江大学的 **CUA-Universe**，研究的就是这种分工怎样批量变成训练数据。论文全名是 *CUA-Universe: A Scalable and Dynamic Environment for Hybrid GUI+CLI Agents*，首版于 2026 年 9 月 4 日提交 arXiv。它把真实软件接入可复现环境，从真实项目文件生成任务，再筛选有效的混合操作轨迹，训练一个 Qwen3.5-9B 模型。［[论文首页与摘要](https://arxiv.org/abs/2609.05374)］

**这篇论文的主要贡献，是一套面向 GUI+CLI 混合 computer use 的自动化环境、任务与训练数据生产方法，并验证这些数据能让小模型更好地选择操作接口。** 大模型在真实应用里执行任务，系统记录截图、动作和返回结果，筛选轨迹，再用于监督微调。数据来自实际交互，而不是仅凭任务描述生成一份操作步骤。

这套方法包含三个相接的环节：给软件搭环境、补工具；生成可执行任务并采集混合操作轨迹；用这些数据训练 Qwen3.5-9B，测量完成率和效率。理解它，可以沿着一条链往下看：**同一份状态 → 两种操作入口 → 可执行的任务 → 有质量的轨迹 → 更合适的接口选择。**

## 一、先把“同时支持 GUI 和 CLI”说清楚

GUI 是图形界面，智能体通过截图理解当前状态，用鼠标键盘操作。CLI 是命令行入口，智能体用命令读取对象、修改参数、执行导出。这里的 CLI 还包括封装在命令后面的脚本 API 和项目文件编辑能力。

两者的边界落在**动作通过什么接口执行**。看截图属于观察；模型看完截图，既可以输出鼠标点击，也可以输出命令。通过应用 API 修改对象，在这套接口里计为 CLI 动作；通过鼠标键盘修改对象，计为 GUI 动作。所以，“使用 CLI”仍然可以依赖视觉理解。

混用发生在每一步：模型根据当前状态选择一个动作，收到结果后再决定下一步。开头的 VS Code 例子就是先在 GUI 里定位，再用 CLI 修改配置。它也可以先批量改文件，再回到界面处理布局。这里没有统一的“CLI 失败才准用 GUI”顺序。［[§3.1、§3.4](https://arxiv.org/html/2609.05374v1#S3.SS4)］

### 没有 CLI 的游戏怎么办

把这个机制外推到游戏：如果环境只暴露画面和鼠标键盘，模型就只能通过 GUI 动作完成游戏操作；混合接口不会自动产生“移动角色”“攻击目标”这样的结构化命令。能否增加 CLI，取决于软件是否提供 API、脚本接口或可操作的项目状态。

论文中的 Godot 是游戏开发编辑器，命令可以编辑场景和项目。编辑游戏工程与操控正在运行的游戏，是两类任务。这篇论文的实验没有验证实时游戏操作；它覆盖的是足够开放或可脚本化的桌面应用。［[附录 C、K](https://arxiv.org/html/2609.05374v1#A3)］

### 两种入口还需要接到同一份状态

难点落在“同一份状态”上。

假设智能体在 Blender 界面里看到了一个模型，又启动一个后台进程修改 `.blend` 文件。磁盘里的对象已经变化，前台 Blender 仍可能显示旧内容。下一步如果根据旧画面继续操作，模型接收到的视觉证据和命令结果就对不上。

因此，混合环境需要把两条操作路径接到同一个项目或运行中的应用上，并处理外部编辑后的界面同步。论文用应用适配器维护这层关系：有些工具直接操作正在运行的软件，有些修改原生项目文件，再通过轻量适配刷新过时的 GUI 视图。［[§3.2 与附录 C](https://arxiv.org/html/2609.05374v1#S3.SS2)］

![GUI 和 CLI 读取、修改同一份应用状态；命令结果和刷新后的截图共同进入下一步观察](/images/posts/cua-universe/shared-state.svg)

*图 1：根据论文 §3.1—3.2 绘制的最小交互模型。两种入口共享任务状态，模型看到的是该状态的截图与命令反馈。*

论文把一个任务写成三个部分：用户指令、初始状态、验收器。智能体每一步收到截图和可选的 CLI 返回结果，再从 GUI 或 CLI 动作中选择一个执行。

这也解释了为什么环境构建会影响模型能力。如果训练环境只提供点击，批量修改十个对象就只能被记录成一串点击；如果环境提供对象级命令，数据里才可能出现“一条命令完成批量编辑，再回到界面处理视觉布局”的路径。**环境暴露的动作，决定了训练数据能教给模型哪些解法。**

## 二、App-Forge：把真实软件变成可重复运行的环境

CUA-Universe 的第一阶段叫 App-Forge。它同时处理软件安装和工具接口，两者都很难靠一份通用脚本覆盖。

### 安装成功，要能沉淀成下一次可复现的配置

安装智能体在持久化虚拟机里安装目标应用、处理依赖、诊断启动失败，直到确认程序能够运行。随后，它把安装过程整理成可复现配置，并提取应用元数据，供后面的任务生成和验收使用。

论文实验中，这部分由使用 GPT-5.6 的 Codex coding agent 完成。同一条适配流程覆盖了 16 个桌面应用，其中 8 个继承自 OSWorld，另外 8 个是新增应用。继承已有环境的部分也需要补上共享状态的 CLI 层。［[§3.2、§4 与附录 B](https://arxiv.org/html/2609.05374v1#A2)］

| 环境来源 | 应用 | 典型初始状态 |
| --- | --- | --- |
| OSWorld 的 8 个应用 | Chrome、GIMP、LibreOffice Calc / Impress / Writer、Thunderbird、VLC、VS Code | 浏览器或邮件配置、文档、媒体文件、工作区 |
| 新增的 8 个应用 | Audacity、Blender、draw.io、Godot、Kdenlive、OBS Studio、QGIS、Zotero | 音频工程、3D 场景、图表、游戏场景、剪辑工程、录制场景、地图项目、文献库 |

### 工具接口按现有能力逐层构建

App-Forge 采用三种办法。

1. **发现现成命令。** 软件已有可用 CLI，就直接包装。例如 Blender 的 `--python-expr`，以及 VLC 的 `cvlc`。
2. **包装脚本 API。** 把 Blender 的 `bpy`、LibreOffice UNO 等接口封装成模型能调用的命令。
3. **生成专用 CLI。** 现有接口不够时，参考 CLI-Anything 的思路，为原生项目文件或运行中的应用生成一组受约束的操作。

附录 C 列出的快照合计约 404 个模型可见命令，OSWorld 应用占 151 个，新增应用占 253 个。各应用的实现方式并不相同：

| 应用 | CLI 后面的真实操作 | 状态落点 |
| --- | --- | --- |
| Blender | 一次后台 `bpy` 执行，读取并修改场景 | 原生 `.blend` 文件 |
| Audacity | 通过 Mod-Script-Pipe 导入、选择、应用音效 | 正在运行的 GUI 工程 |
| LibreOffice Writer | 经 live UNO bridge 操作文档、表格和样式 | 当前文档及原生文件 |
| draw.io | 操作 XML / mxGraph 中的页面、形状和连接线 | 原生 `.drawio` 文件 |
| Kdenlive | 编辑 MLT XML，配合 `melt` 渲染 | 原生 `.kdenlive` 工程 |
| Chrome | DOMShell 暴露页面、可访问性树与元素操作 | 浏览器页面状态 |

模型面对的是工具 ID、描述和命令模板。运行器把选择展开成具体命令，必要时注入当前工作文件路径，在虚拟机内执行，再把退出码及输出返回给模型。一次失败于是可以被识别为“命令返回错误”，而不必只凭界面有没有变化猜测。［[附录 C](https://arxiv.org/html/2609.05374v1#A3)］

从这里看，“支持 16 个软件”的实际工作量包括安装、原生格式、运行时接口和视图同步。命令数量展示了接口覆盖范围；每个命令能否可靠地改变目标软件，才是环境能否产出有效数据的前提。

## 三、Task-Weave：怎样避免生成一堆做不了的任务

环境可用以后，还需要大量任务。直接让模型编写“请修改某个文件”很容易出现三个问题：目标对象根本不存在，指令有歧义，或者初始文件已经满足要求。

Task-Weave 用真实初始状态和实际交互收紧生成范围。它的流程是：探索软件，提炼操作，组合任务，再回到软件里检查。［[§3.3](https://arxiv.org/html/2609.05374v1#S3.SS3)］

![App-Forge 产出环境与工具，Task-Weave 生成并检查任务，Path-Steer 采集和筛选轨迹，最终供 9B 模型监督微调](/images/posts/cua-universe/pipeline.svg)

*图 2：三阶段流水线的中文重绘。Path-Steer 的任务级引导用于数据采集；评估时该字段为空。*

### 第一步：从真实交互提炼高层操作

探索智能体围绕不同目标操作软件，例如检查结构与可见性、修改外观、管理导出。系统记录截图和动作，用滑动窗口读取轨迹，再让语言模型提炼可复用操作。

这个抽象的粒度是 `export_scene_to_gltf`，也就是“把场景导出成 glTF”；底层点击只是完成它的过程。系统还记录执行方法，过滤琐碎或不可复用的候选，再去重、聚类，形成带有交互证据的操作池。

这样，一个窗口里发生过的具体点击，才能变成可组合到其他任务中的能力。

### 第二步：用真实 seed 限定任务可以引用什么

seed 可以理解为任务起点：一份已经加载到软件里的真实工程，以及描述其中对象的元数据。

附录 D 给出的例子包括 Blender 的实体模型、Calc 的预算表、Impress 的照片幻灯片和 draw.io 的流程图。seed 由 coding agent 从公共仓库与素材库搜索、下载，再做格式转换，归一化成适合任务生成的项目状态。［[附录 D](https://arxiv.org/html/2609.05374v1#A4)］

有了这个起点，任务生成器才能判断“修改某个形状的颜色，再连接到另一个节点”是否有意义：初始图里需要真的有这些节点，命令层也需要能操作它们。

随后，系统采样操作链，对链条与 seed 的匹配程度评分。任务难度通过链长和组合方式控制，从单步修改延伸到多步骤混合工作流。最终生成的任务包包括指令、初始状态、验收器和引导信息；给执行者的指令表达用户目标，具体操作路径留给智能体选择。

### 第三步：短程试运行，修掉不成立的任务

一个 ReAct 风格的审查智能体启动软件，做一小段多模态交互，检查任务是否可行、是否明确、是否已经完成。能修的任务修改指令或引导，无法成立的任务丢弃。

这一层的作用很直接：在花费几十步采集完整轨迹之前，先发现“题目本身有问题”。它用实际执行检查生成的指令是否成立。

## 四、Path-Steer：工具开放以后，还要教模型怎么选

给模型一组 CLI 工具，并不保证它会使用。论文的 CUA-Verse 行为统计中，基础 Qwen3.5-9B 的 CLI 动作占比是 **0%**。工具已经放在面前，它仍沿着原来的 GUI 路径执行。

**Path-Steer 是用于生成训练轨迹的软件流程。它的“Steer”，具体通过任务级提示文本引导执行模型选择 GUI 或 CLI。** 论文没有把它定义为一个独立训练的模型，也没有给它配置一个专门负责路由的更高级模型。

一次 rollout 是智能体从初始环境开始，尝试完成任务的完整执行过程。Path-Steer 包含三个部分：在同一条轨迹中执行 GUI 和 CLI 动作，提供效率导向的路径提示，以及评分、保存高质量轨迹。批量修改、精确数值、吞吐量高的操作偏向 CLI；依赖视觉布局和界面状态的操作偏向 GUI。［[§3.4](https://arxiv.org/html/2609.05374v1#S3.SS4)］

### 谁决定下一步用 GUI 还是 CLI

具体动作由正在执行任务的模型输出。数据采集与最终评估使用的模型不同：

| 阶段 | 执行动作的模型 | 收到的路径信息 | 谁选择下一步接口 |
| --- | --- | --- | --- |
| 主要训练数据采集 | Kimi K2.5 | 通用分工原则、可用工具、本任务的 Path-Steer 引导 | Kimi K2.5 |
| 微调模型评估 | 训练后的 Qwen3.5-9B | 通用工具使用规则和可用工具；任务路径提示为空 | Qwen3.5-9B |

运行器接到模型输出后，才把 GUI 动作送去执行鼠标键盘操作，把 CLI 动作展开成命令并在虚拟机里执行。这一层按动作类型分发，负责把动作执行出来；本次任务该怎样拆解、何时切换接口，由模型结合提示和反馈决定。

评估仍保留通用规则，例如对工具覆盖的文件检查、编辑、保存和导出优先使用 CLI，视觉任务或缺少合适工具时使用 GUI。**评估移除的是针对当前题目的路径提示。** 这一区别决定了怎样理解“训练后的模型自己选择”。［[附录 E、I 与评估提示 Figure 12](https://arxiv.org/html/2609.05374v1#A9)］

### 在实现层面，路径提示怎样进入模型

沿着论文公开的字段和消息格式，可以追到下面这条调用链：

1. **任务包携带 guidance。** Task-Weave 把操作链、seed、交互证据和对应 CLI 工具组合成任务包，其中包括引导信息；试运行审查还可以修改这份引导。
2. **把引导放进系统提示。** Figure 10 明确展示了字段 `[Task guidance for this attempt: First ...]`。任务级建议通过这段文字传给执行模型，与 GUI 操作说明和 CLI 工具列表一起生效。
3. **模型逐步输出动作。** 每轮输入包含任务、当前截图、动作历史和 CLI 结果历史。输出格式包含 `Action` 和 `Code`，代码部分可选择 GUI 的 Python／`pyautogui` 动作或 CLI 命令块，也可等待、结束。
4. **执行结果进入下一轮。** CLI 返回 `rc` 和 `output`，运行器把结果放回观察中。模型可以继续命令操作，也可以切回界面；完成后，系统评分并保留高质量轨迹。

这说明 Path-Steer 的引导落在提示文本上，动作选择落在执行模型上，动作分发落在运行器上。［[§3.3](https://arxiv.org/html/2609.05374v1#S3.SS3)、[Figure 10](https://arxiv.org/html/2609.05374v1#A11.F10)］

论文对“怎样从操作链生成 guidance”只给出了方法描述，没有给出完整生成算法、提示模板或对应源码。能确认的是引导的来源、用途和注入位置；具体是否使用固定规则、如何调用模型或拼装模板，公开材料不足以判断。因此，不能把 Path-Steer 具体说成一张写死的 GUI／CLI 路由表，也不能把未披露的部分补成一个额外规划模型。

一个有用的例子来自 VLC：带引导的轨迹先尝试 VLC 参数，遇到无效路径后转用 `ffmpeg` 完成视频旋转，再处理需要 GUI 的音频效果面板；未引导轨迹则在滤镜配置阶段反复搜索和点击，最后失败。这个案例说明，高质量轨迹也可以包含试错，关键在于收到失败反馈后能换到可行路径。

### 把接口相同的两组放在一起，才能看出引导的贡献

论文在固定的 320 个合成任务上，保持 CLI 工具可用，只切换 Path-Steer。验收通过的条件是评分至少 0.75。［[表 3](https://arxiv.org/html/2609.05374v1#S4.T3)］

| 数据生成模型 | Path-Steer | 通过比例 | 平均分 | 平均步数 | 平均 token / 任务 |
| --- | --- | ---: | ---: | ---: | ---: |
| Kimi K2.5 | 关闭 | 44% | 0.63 | 26.68 | 385,107 |
| Kimi K2.5 | 开启 | 51% | 0.71 | 22.75 | 331,988 |
| Seed2.1 Pro | 关闭 | 45% | 0.67 | 28.78 | 303,653 |
| Seed2.1 Pro | 开启 | 54% | 0.75 | 25.53 | 263,500 |

Kimi 的通过比例增加 7 个百分点，步数和 token 同时下降；Seed2.1 Pro 也呈现同方向变化。这组对照支持一个明确判断：在已有工具之外，任务级的接口选择引导还能提高数据产出质量。

论文估算的 Kimi 单任务成本从 0.31 美元降到 0.26 美元。若按“平均成本 ÷ 通过比例”粗算，每条合格轨迹的采集成本约从 0.70 美元降到 0.51 美元。这个计算使用表 3 的四舍五入数据，衡量的是该组 rollout 的采集产出，未计入环境构建、任务合成和训练开销。

## 五、哪些轨迹能进入训练集

执行完任务，并不意味着这条轨迹值得学。CUA-Universe 用 GPT-5.4 作为视觉语言模型评分器，读取任务指令、压缩后的操作轨迹及按时间采样的截图，返回 0 到 1 的分数与简短理由。

评分器最多读取 15 张截图。视觉任务以最终画面为主要证据；如果任务明确要求交付文件，评分规则会结合 CLI 结果与导出产物证据，处理“文件已经改变、GUI 尚未刷新”的情况。这个规则和前面的共享状态设计是连在一起的：验收要知道目标究竟是屏幕状态，还是交付文件。［[附录 F](https://arxiv.org/html/2609.05374v1#A6)］

论文还做了人工复核。16 个应用各抽取 30 条已通过、30 条未通过轨迹，总计 960 条，由 3 名标注者在不知道机器评分的情况下独立判断。

- 480 条机器通过的轨迹中，人工认为 475 条完全成功、5 条部分成功，样本通过集精确率约 99.0%。
- 480 条机器拒绝的轨迹中，有 25 条被人工认为完全成功。
- 按各应用真实通过比例重新加权后，论文报告人机一致率 97.0%，Cohen’s κ 为 0.94。

这组结果支持把评分器用于高质量轨迹筛选，同时显示它会损失一部分可用数据。99.0% 描述的是这次抽样通过集的精确率；文章后面使用的 CUA-Verse Score，仍是模型评分器给出的平均任务分数。

### 最终训练配方

Kimi K2.5 负责操作抽象、任务合成和执行轨迹生成。评分达到 0.75 的轨迹被保留，最终得到 **4,923 条完整轨迹、235,408 条 step-level 记录**。包含截图的落盘数据约 286.64 GB。［[§4 与附录 H](https://arxiv.org/html/2609.05374v1#A8)］

| 项目 | 论文设置 |
| --- | --- |
| 基础模型 | Qwen3.5-9B |
| 训练方式 | 监督微调，LoRA |
| LoRA | rank 8，alpha 32，dropout 0.05 |
| 更新范围 | 语言模型的线性模块；基础权重、视觉塔与多模态对齐器冻结 |
| 学习率与训练轮次 | `1e-4`，3 epochs |
| 最大序列长度 | 18,000 |
| 训练框架与资源 | ms-swift，8 张 A100，约两天 |

这里学习的是“观察到这些状态和反馈时，下一步该采取什么动作”。采集阶段负责找到并筛选路径，监督微调让模型学习这些路径上的动作选择。论文实验没有使用强化学习，评分器在当前流程中的直接职责是验收和过滤。

## 六、实验一：同一个 9B 模型，接口选择真的变了吗

CUA-Verse 有 160 个保留测试任务：8 个新增应用，每个应用 20 题。测试任务与训练任务分离，应用本身在训练范围内。这组实验测量的是已覆盖软件上的新任务执行能力。［[§4.1 与表 1](https://arxiv.org/html/2609.05374v1#S4.SS1)］

| 模型 | 平均 Score，0—1 | 平均步数 | 平均 token / 任务 |
| --- | ---: | ---: | ---: |
| Qwen3.5-9B 基础模型 | 0.189 | 56.2 | 643K |
| EvoCUA-8B | 0.330 | 41.7 | 377K |
| CUA-Universe 微调模型 | **0.582** | **35.2** | **255K** |
| Kimi K2.5 | 0.522 | 21.1 | 275K |
| Seed2.1 Pro | 0.599 | 40.1 | 449K |
| GPT-5.5 | 0.768 | 23.1 | 193K |

同一基础模型微调后，Score 增加 0.393，平均步数下降约 37%，token 下降约 60%。0.582 是部分完成也可能获得分数的平均评分，阅读时应与下一节的二元成功率分开。

行为统计补上了机制证据：基础模型的 CLI 动作占比为 0%，微调后变成 25.3%。因此，分数变化伴随着真实的动作分布变化，模型开始利用工具完成原先依赖 GUI 的操作。［[附录 A.1、表 4](https://arxiv.org/html/2609.05374v1#A1.SS1)］

微调模型的平均分超过数据生成模型 Kimi K2.5。作者给出的解释是，训练保留了教师的高分轨迹，学生学习的是经过筛选的行为，而教师在测试时仍可能产生失败轨迹。这个结果发生在这组应用和任务上，GPT-5.5 的分数仍更高。

应用之间也有明显差异。微调模型在 Audacity 上得分 0.815，在 Blender 上为 0.398，在 Godot 上为 0.460。音视频任务和 3D、空间任务对模型提出了不同要求，平均分不会替代这种能力分布。

表 4 还有一个很有意思的现象：GPT-5.5 的记录动作全部被归为 CLI，却拿到最高平均分。这提示我们区分“看截图”和“执行鼠标动作”：只发出 CLI 动作的模型仍然接收视觉观察。参考解法混合两类操作，也不足以证明每道题都必须实际执行 GUI 动作。最有说服力的证据，是同一基础模型学会调用 CLI 后，完成度和效率一起改善。

## 七、实验二：在 OSWorld 上，把训练收益和接口收益拆开

OSWorld 这组实验使用 244 个任务，排除了 `os` 和跨应用类别，每个任务最多 60 个模型决策步骤。成功率 SR 按官方验收器奖励是否等于 1 计算。GUI+CLI 组获得应用命令定义和输入文件路径，其他任务文本、环境设置及验收器保持一致。［[§4.2、表 1](https://arxiv.org/html/2609.05374v1#S4.SS2)］

最值得看的，是 Qwen3.5-9B 的四个格子。

| 模型 | 仅 GUI | GUI+CLI | 增加 CLI 的变化 |
| --- | ---: | ---: | ---: |
| 基础 Qwen3.5-9B | 21.7% | 24.6% | +2.9 个百分点 |
| CUA-Universe 微调后 | 23.4% | 40.2% | **+16.8 个百分点** |

![OSWorld 244 题子集的四组结果：基础模型 GUI 21.7%、混合 24.6%；微调模型 GUI 23.4%、混合 40.2%](/images/posts/cua-universe/osworld-results.svg)

*图 5：按论文表 1 重绘。横轴从 0 开始，四根柱子对应同一评估子集；比较方向决定增益的含义。*

横向看，未训练时增加 CLI，收益只有 2.9 个百分点；混合训练后再开放 CLI，收益达到 16.8 个百分点。纵向看，保持 GUI+CLI 接口不变，微调使成功率从 24.6% 升到 40.2%，增加 **15.6 个百分点**。

这四个格子比一句“提升 16.8%”能说明更多问题：训练和工具入口相互配合，主要改善集中在模型利用 CLI 的能力上。仅 GUI 条件下，微调前后的变化较小。

再看效率，同一个微调模型从 GUI 切到 GUI+CLI，全体任务的平均步数由 39.6 降到 28.6，平均 token 由 325.7K 降到 286.5K，分别下降约 28% 和 12%。

论文还给出另一种口径：只取两种接口都成功完成的题目，逐题计算 GUI 成本与混合成本之比，再求平均。微调模型的 Step Gain 是 2.35，Token Gain 是 1.79，回答的是“同一道已经能做对的题，改走混合路径能省多少操作”。摘要约 57% 的步数节省和 44% 的 token 节省，与这两个比值的倒数换算相符。它们和上一段全体任务均值的分母不同。

在这组 OSWorld 子集上，EvoCUA-8B 的混合成功率为 43.3%，GPT-5.5 为 68.0%；CUA-Universe 的 40.2% 体现了同底座的明显进步。比较排行榜时，应继续沿用这组题目和运行协议。

## 八、实验三：换成 MCP，或者换一批软件，还能迁移多少

### 换工具调用格式：OSWorld-MCP

OSWorld-MCP 给智能体提供 158 个 MCP 工具，允许它们与 GUI 动作组合。论文使用其中 244 个任务，包括 159 个适合工具辅助的任务和 85 个非工具受益任务，步数上限为 50。

训练使用的是应用专用 CLI，评估换成此前未在训练中出现的 MCP 动作接口。这组实验检验接口选择能力是否能跨调用格式迁移。［[§4.3 与表 2](https://arxiv.org/html/2609.05374v1#S4.SS3)］

| 指标 | 基础 Qwen3.5-9B | 微调模型 |
| --- | ---: | ---: |
| SR | 20.90% | 28.69% |
| TIR，工具使用决策准确率 | 10.66% | 23.36% |
| ACS，平均完成步数 | 37.22 | 27.25 |
| Tok，表中单位 M | 125.68 | 87.95 |

成功率提高 7.79 个百分点，工具决策准确率提高 12.70 个百分点，ACS 下降约 27%，表中 token 统计量下降约 30%。这说明训练收益有一部分可以跨接口格式保留下来。

该版论文摘要还报告 Score 增加 7.84 点，正文另提 Score 29.51%；表 2 展示的是 SR 28.69%。这里按表 2 比较同名指标。表 2 对 token 标注了 M，但正文没有一致交代其聚合分母，因此保留原表单位，仅比较相同口径下的相对变化。

### 换软件：只用不重叠的 8 个应用训练

完整训练集已经包含 OSWorld 的应用。要判断“换软件还会不会”，需要把这些应用从训练中拿掉。

附录 A.2 做了这个实验：只用另外 8 个应用训练 LoRA，再在 OSWorld 的 8 个应用上测试。该表报告的基础成功率是 24.2%，只用域外应用训练后为 27.4%，加入域内应用的完整训练为 40.2%。［[附录 A.2、表 5](https://arxiv.org/html/2609.05374v1#A1.SS2)］

这个结果把两种收益区分开了：跨软件的通用操作能力带来 3.2 个百分点提升，加入目标应用数据后，完整配方还能再提高 12.8 个百分点。域外训练在 8 个应用中的 7 个上改善，Impress 下降 1.9 个百分点，迁移效果与应用有关。

表 5 的基础值 24.2% 与表 1 的 24.6% 不同，附录文字中的部分增益也与表值不一致。这里限定在表 5 内做差：`27.4 - 24.2 = 3.2`，`40.2 - 27.4 = 12.8`。两种训练配方的数据覆盖也不同，这组实验展示的是配方收益，尚未把应用覆盖和训练数据量的影响完全拆开。

## 九、这条路线的工程价值落在哪里

CUA-Universe 把增加软件环境、增加任务和增加训练数据连接起来。一个应用完成适配之后，可以在不同 seed 上生成更多操作组合，采集更多路径，再用验收器挑出值得学习的部分。它为“训练模型使用电脑”提供了一条持续扩充数据的路线。

相关工作里，CoAct-1 已经组合 GUI 操作者和 coding agent，UltraCUA 也研究混合动作模型。CUA-Universe 的重点进一步落到真实应用的适配与环境到数据的生产流程上：工具围绕应用构建，任务围绕真实状态组合，轨迹带上接口选择信号。［[§2.3](https://arxiv.org/html/2609.05374v1#S2.SS3)］

从论文机制可以推导出几个具体的工程检查点。

**先检查状态是否接通。** 同一文件经 CLI 修改后，GUI 是否仍显示旧内容；命令操作的是当前工程还是另一个路径；退出码、结构化返回和界面状态能否互相核对。混合策略建立在这层一致性上。

**把接口选择放进数据评估。** 除了成功率，记录模型是否调用已有工具、哪些任务开始使用 CLI、遇到失败是否切换路径。基础模型 CLI 占比为 0% 的现象，比笼统地说“模型不会用工具”更容易定位。

**按交付物选择验收证据。** 用户要求导出文件，就检查文件对应的内容证据；用户要求界面进入某种状态，就检查最终画面。对一个本来只要求文件导出的任务反复截图，可能增加成本；只要求界面状态的任务，单凭命令成功又可能漏掉未完成的部分。

**用每条合格轨迹的成本衡量采集。** rollout 平均便宜了多少，和最终留下多少可训练数据，需要一起看。Path-Steer 的意义同时体现在通过比例和执行开销上。

附录 G 也说明了这类系统的资源特征：单个虚拟机配置为 4 vCPU、4 GB 内存，每步动作后等待 3 秒再观察。作者用约一万次 rollout、平均约五分钟估算采集工作量，在一台 128 核机器上运行约 32 个环境，实际报告约 1.3—1.5 天。这里描述的是环境执行端的并行规模；生成模型与评分模型的推理服务，以及后续 8 张 A100 的训练，是另外的资源项。［[附录 G](https://arxiv.org/html/2609.05374v1#A7)］

## 十、沿着论文继续验证什么

当前证据覆盖 Linux 桌面、单应用任务，以及足够开放或可脚本化的软件。跨应用工作流、封闭软件适配和强化学习，是作者留给后续的方向。正文提出将发布代码与数据；截至 2026 年 9 月 8 日，本文尚未核实到论文对应的代码、数据下载入口。［[附录 K](https://arxiv.org/html/2609.05374v1#A11)］

如果要沿着这项工作做复现，我会先选开头的 VS Code 设置任务，把初始配置、GUI 状态和最终文件固定下来，分别跑基础模型与微调模型的 GUI / GUI+CLI 四种组合。对每条轨迹记录成功与否、模型决策次数、token，以及从 GUI 切换到 CLI 的位置。

这个小实验能检查整篇论文最关键的因果链：工具入口是否真的接入同一状态，训练后的模型是否开始选择它，以及这种选择是否同时改善完成度和成本。把这条链跑清楚，再扩到第二个应用，环境、任务与轨迹的价值才会逐步显现。
