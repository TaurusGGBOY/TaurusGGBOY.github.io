# Agent 主题对比系列差异优先重写设计

日期：2026-08-28

## 重写原因

上一版虽然摆脱了源码目录结构，却把大量正文用在四个 Agent 的共同机制上。量化检查显示，前七篇有 48%–72% 的正文段落完全不提任何产品；直接同时比较两个以上产品的内容通常只有 6%–15%。读者看完知道 Agent 大致怎样工作，仍然难以回答 Claude Code、Codex、Pi、DeepSeek Harness 之间该怎样选。

本轮不再修补旧段落。九篇正文再次从零重写，删除所有不承担差异判断的共性科普。文件名和公开 URL 保留；标题、主题顺序、摘要和正文必须按本设计更新。

## 核心目标

每篇文章只回答一个比较问题：四个项目在同一维度上采取了什么不同选择，这些选择分别带来什么优势、短板、隐藏成本和适用条件。

文章可以在具体维度上明确判断谁更完整、更自由、更稳定、更容易集成或风险更高，但判断必须限定在公开资料支持的范围内。系列不生成脱离场景的总冠军。

## 删除规则

以下内容全部删除，唯一例外是解释某项具体差异所必需的一句共同场景基准：

- 四者都会读文件、调用工具、修改代码、运行测试等功能共性；
- 通用 Agent loop、上下文工程、沙箱定义、多 Agent 定义等入门科普；
- 与某一产品差异无关的任务准备建议；
- 每篇重复出现的产品定位、成熟度说明和安全免责声明；
- 为凑齐四个产品而写的等长介绍；
- 只说明“具体情况取决于配置”却没有给出选择后果的段落。

只有解释差异所必需的共同基准可以保留，例如用一句话说明同一危险命令或同一断线场景。产品无关内容不得超过正文汉字数的 10%。

## 统一写法

采用“正面对比 + 场景裁决”结构：

1. 开头直接给出本维度的主要差异和初步判断；
2. 用一个具体任务或事故作为共同输入，不展开通用流程；
3. 按最有解释力的冲突轴组织正文，而不是机械地按四个产品轮流介绍；
4. 每个冲突轴至少比较两个产品，并说明设计选择如何改变使用结果；
5. 对每个重要判断写清优势、短板、隐藏成本和适用条件；
6. 结尾用“优势 / 短板 / 代价 / 适合谁”裁决表收束；
7. 文末只列正文实际引用的公开来源。

允许篇幅不均。某个产品在本维度没有鲜明设计时可以只写一段；差异最大的两个产品应得到更多篇幅。文章不为形式完整而平均分配字数。

## 九篇新架构

### 01｜四种 Harness 到底把控制权交给谁

- 比较冲突：产品替你决定工作流，还是团队自己拥有运行时。
- 重点差异：Claude Code 的集成式产品控制；Codex 的 Harness 与客户端协议；Pi 的最小核心；DeepSeek Harness 的插件化运行时。
- 必须回答：采用后最难替换的部分是什么，团队接手了哪些责任。
- 删除：模型与 Harness 的通用定义、共同任务循环、评测任务卡。

### 02｜默认工具越多越好吗

- 比较冲突：内建工具与工作流带来的即时生产力，对比最小工具面带来的可控性。
- 重点差异：Claude Code 与 Codex 的产品化工具面；Pi 的小核心与扩展责任；DeepSeek Harness 的工具注册与插件组合。
- 必须回答：开箱能力、工具结果质量、定制成本、工具失效时的排查责任分别落在哪里。
- 删除：六步 Agent loop、四者都会执行工具、通用失败分类。

### 03｜谁真正替你隔离危险命令

- 比较冲突：内建沙箱和审批，对比完全依赖外部隔离或实验性插件边界。
- 重点差异：Claude Code 与 Codex 的权限/沙箱组合；Pi 明确不内建沙箱；DeepSeek Harness 的审批与沙箱设计仍处实验预览。
- 必须回答：不额外配置时谁承担风险，哪种边界最容易被误解。
- 删除：沙箱、审批、容器的教科书定义和通用低风险动作列表。

### 04｜会话中断后，四者各自能恢复什么

- 比较冲突：产品级 transcript、服务端 thread、显式 JSONL 树和可替换事件日志。
- 重点差异：Claude Code 的 resume/fork/compact；Codex 的 thread/turn/item；Pi 的树形 session；DeepSeek Harness 的 append-only event log。
- 必须回答：恢复的是聊天、控制状态、代码环境还是分支路径；哪些部分仍需用户自己校验。
- 删除：大窗口不等于记忆、交接物通用模板、通用恢复建议。

### 05｜从 CLI 切到 IDE 或云端，状态会不会断

- 比较冲突：多个产品入口与一套可驱动运行时之间的区别。
- 重点差异：Claude Code 各工作台的会话边界与 teleport；Codex App Server；Pi 的 TUI/RPC/SDK；DeepSeek Harness 的 profiles。
- 必须回答：谁持有状态，客户端消失后任务是否继续，集成者需要维护什么协议。
- 删除：状态包含哪些内容、断线与并发的通用概念。

### 06｜扩展越深，升级越痛

- 比较冲突：稳定扩展点、进程内扩展和可替换运行时之间的维护代价。
- 重点差异：Claude Code 的分层扩展与插件打包；Codex 的 AGENTS/Skills/MCP/App Server；Pi 的 TypeScript extensions；DeepSeek Harness 的 everything-is-a-plugin。
- 必须回答：能改多深、最坏能破坏什么、升级时谁负责兼容。
- 删除：Skill、MCP、Hook 的通用定义和扩展清单管理建议。

### 07｜多 Agent 是成品能力还是自建工程

- 比较冲突：内建 subagent/team、工作流编排、扩展实现和异构 provider 抽象。
- 重点差异：Claude Code 的集成入口；Codex 的任务/审查工作流与集成面；Pi 的扩展自建；DeepSeek Harness 的 provider/transport 组合。
- 必须回答：并行、任务所有权、结果汇合和跨产品调用分别由谁实现。
- 删除：多 Agent 四层定义、通用任务图、A2A 入门说明。

### 08｜谁最容易证明任务真的完成

- 比较冲突：产品内建验证习惯、可接入的运行态反馈、使用者自建门禁和事件可观察性。
- 重点差异：Claude Code 的工具与 hooks；Codex 的运行态反馈和 Harness engineering 取向；Pi 的验证扩展责任；DeepSeek Harness 的事件与 telemetry 组合。
- 必须回答：默认能留下什么证据，缺失部分由谁补，哪种组合最容易产生“说完成但无法复查”。
- 删除：测试、Trace、停止条件和总成本的通用定义。

### 09｜四种 Agent 怎么选：看你愿意承担什么责任

- 比较冲突：购买整合度、复用执行层、拥有最小核心、重组完整运行时。
- 重点差异：把前八篇的维护、安全、集成、恢复和验证责任压缩成选择条件。
- 必须回答：个人开发者、产品集成团队、内部平台团队和运行时研究者分别优先看谁，以及哪些条件会让建议反转。
- 删除：重复介绍四个项目、宽泛试点建议和无结论的功能表。

## 内容密度指标

每篇目标为 2,200–3,200 个汉字，不以达到下限为理由重复背景。

静态审查采用以下指标：

- 产品无关段落的汉字数不超过正文 10%；
- 同时比较两个以上产品的段落不少于正文 35%；
- 其余产品相关段落必须承担优势、短板、代价或适用条件之一；
- 每个非来源二级标题下至少出现两个产品，或有一张覆盖至少两个产品的对照表；
- 每篇至少出现四个明确短板，且四个产品的短板在全系列中都有具体证据；
- 每篇结尾必须有裁决表，不使用纯功能勾选表；
- 同一产品定位句不得跨篇原样重复。

这些指标用于发现失焦，不替代人工审读。产品专节可以只出现一个产品名，但前后必须有直接对照段落，不能变成孤立说明书。

## 证据边界

继续只使用公开官方文档、官方工程文章、项目 README、安全说明和方法透明的研究材料。本地源码、反编译结果、本站旧文与上一版正文不承担事实证据。

官方文档可以证明设计和产品行为，不能证明质量排名。公开工程案例只能说明特定仓库中的方法，不外推普遍性能。DeepSeek Harness 的 developer preview、兼容性变化和安全边界只在相关主张旁简短说明；03、06、07、09 必须明确出现。在 01、02、04、05、08 中，只有当正文引用其预览期架构或据此给出适用性判断时，才在首次相关判断旁加入一句成熟度限定；否则不写。不得复制整段免责声明。

## Frontmatter 与发布约束

- 保留九个文件名、published、image、imagePosition、slug、series 和 order；
- 更新 title、description、tags、topics、prerequisites、time、updated 和 verified_at；
- 保留站点必需的 category 与 draft；
- 正文不重复 frontmatter 封面，不新增无论证作用的插图；
- 九篇全部完成后统一执行证据边界审查、站点检查、单元测试、生产构建、产物验证、浏览器测试、GitHub Pages 部署和线上逐页验证。

## 完成定义

以下条件全部满足才算完成：

1. 九篇正文按新架构从零重写；
2. 产品无关内容与直接比较比例通过静态检查和人工复核；
3. 每篇的优势、短板、代价和适用条件能够从正文与裁决表对应；
4. 没有共性科普、旧源码证据、重复免责声明或平均分配的产品介绍；
5. `press-conference-revision-evidence-bound` 审查没有抬高主张；
6. 本地检查、CI、Pages 部署与九个线上 URL 全部通过。
